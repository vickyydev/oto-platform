# DESIGN ops-scale-delivery

## Summary
The cloud side of OTO is small: about 10 boxes, 15 iPads, and well under 50 requests per second at peak. One Render API instance and a 1 CPU Postgres are enough, and I agree with the brief's "no HA" decision because the boxes provide the availability. The difficulty is in three other places, and the design spends its effort there:

1. **Never losing or duplicating a box event**, including after a cloud point-in-time restore.
2. **Keeping three separately deployed artifacts compatible**: the cloud API, the PWA and the box agent. Some boxes may have been offline for weeks.
3. **Operating Pis in a Phuket mall remotely**, over metered cellular, with no UPS.

Nothing was run for this review. It is a read-only analysis based on the brief, the four reconnaissance maps, and the repo files I read directly (the API entry point, app composition, env, database pool, platform schema, CI workflow, docker-compose and ARCHITECTURE.md).

**Recommended shape**
- One origin, `app.otoplay.co`, where Fastify serves the launcher and every staff app by path. Single sign-on then stays "the same cookie".
- WebSocket to the boxes carries only wake-up pokes and commands. All data moves over idempotent HTTPS batches. This removes any need for sticky sessions.
- The cloud owns each box's acknowledgement cursor. Boxes number their events and keep acknowledged events for 14 days, so a restore heals itself on reconnect.
- The agent ships as a signed tarball with the Node runtime and the app bundle split, so a routine update is about 3 MB. Rollout is staged through channels with health-checked rollback.
- Fleet telemetry lives in Postgres. There is no Prometheus or Loki stack.

**Where I push back on the brief**
- A shared HMAC key on every box. I would limit HMAC to wristbands and use Ed25519 everywhere else.
- A DNS API token on every box for Caddy DNS-01. I would have the cloud run ACME on the boxes' behalf.
- dnsmasq on two boxes. I would use the router's static DNS where the router supports it.
- Caching the whole operator's member base on stealable Pis.
- Archiving audit after 12 months. Thai accounting retention is commonly 5 years or more.
- Treating the UPS as a wish-list item. It should be a go-live condition.

**Delivery, frankly.** The remaining POS scope plus the foundation rework is roughly 50 to 75 engineer-weeks, by my de-duplication of the four maps' estimates. Rebuilding the suite adds roughly 25 to 40 more, and that part cannot be sized until the Replit apps are inspected. This is a programme, not one sprint. I would run it as one continuous effort with gated, demoable milestones:

1. Start a parallel hardware-spike track in week 1. A simulator-only plan pushes all the real risk to the end.
2. Deliver the launcher first by linking out to the legacy apps as they are.
3. Fold modules into the central database one at a time, and only after the POS is live.

**Rework before building further**, in order: the live authorisation defects; then the service layer and transactions; schema-per-module; change tracking; box, station and device tables; account-or-device principal with signed tokens; event-ledger sync; module registry; deployable artifacts and CI.

## Key decisions
- **Serve the launcher and every staff app from one origin (`app.otoplay.co`) by path, with Fastify serving the static bundles. The public booking site and marketing website stay on separate origins that never receive the session cookie.** — The existing host-only `oto_session` cookie becomes single sign-on with no change to `apps/api/src/plugins/session.ts`. API and frontends deploy atomically, which removes one axis of version skew. `apps/pos/vite.config.ts` already honours `BASE_PATH`. Static traffic is negligible for about 20 staff on a precached PWA. (rejected: Subdomains with a `Domain=.otoplay.co` cookie: the cookie would be sent to the marketing site and to every `*.central.otoplay.co` box hostname. A central OIDC auth service: ten or more days of work for no benefit at this size. Render static sites with proxy rewrites to the API: relies on rewrite behaviour I could not verify, and splits deploys.)
- **Run one API process with switchable roles (`PROCESS_ROLES=api,ws,jobs`). Jobs run in-process on the shared pool to start, and can be split into a second service by config later.** — On Render a separate worker is a separate process and therefore a separate pool, so this is the only honest way to meet the brief's one-pool rule. Rollups are SQL work done by Postgres, not by Node, so in-process jobs do not starve the event loop. Splitting later costs nothing if roles exist from day one. (rejected: A dedicated worker service from day one (more cost and connections for no current need). Render cron jobs for every task (each opens its own connection and has no retry semantics).)
- **The box WebSocket carries authentication, heartbeat, pokes and commands only. All data moves over idempotent HTTPS batches (`POST /sync/push`, `GET /sync/pull`). Commands are rows in `box_command`, fanned out across instances by Postgres `NOTIFY`.** — No sticky sessions and no state that matters if a socket drops or an instance restarts. HTTP gives acknowledgement, retry and observability for free. Deploys that kill sockets become harmless. The design works unchanged at one instance or five. (rejected: Streaming sync data over the WebSocket with hand-rolled acks and ordering (this is where sync bugs live). Sticky sessions or a separate stateful gateway service. Redis pub/sub (another service for a fleet of tens).)
- **The cloud owns each box's acknowledgement cursor. Every event has a per-box monotonic `box_seq`. Boxes keep acknowledged events for 14 days, and the sync handshake replays from the cloud's cursor if it is behind.** — A cloud point-in-time restore silently loses events that boxes had already been told were safe. With this design a restore heals itself on reconnect, and re-ingest is a no-op where data survived. The cloud orders events per box by sequence and never by clock time. (rejected: Delete-on-ack outboxes (data loss after any restore). Ordering or deduplicating by timestamps (breaks on the first Pi with a dead RTC).)
- **Partition `audit_log` monthly on server-recorded time now, dedupe replays through the non-partitioned `sync_event` ledger, archive cold partitions to object storage, and retain financial and child-release audit for at least five years.** — It costs about a day while the table is nearly empty. Unique indexes on partitioned tables must include the partition key, so replay dedupe cannot live on the audit table itself. Box clocks cannot be trusted as a partition key. (rejected: Partitioning on `occurred_at` (rows scatter into wrong partitions when a box clock is wrong). Deleting audit after twelve months as the brief suggests (conflicts with accounting retention). Deferring partitioning until the table is large (painful rewrite).)
- **Rollups are plain tables in an `analytics` schema, upserted per branch business day, with a `dirty_day` marker set by the sync ingest so late offline events trigger recomputation. 'Today' tiles read OLTP directly.** — Offline boxes deliver yesterday's sales tomorrow. A closed-day rollup that cannot be recomputed becomes wrong silently. Materialized view refresh recomputes everything and takes locks. (rejected: Materialized views. A read replica first (the brief correctly says rollups first). Letting each imported analytics app query OLTP freely.)
- **Backups are Render PITR plus a nightly encrypted `pg_dump` to a bucket in a different account, with a quarterly restore drill that runs a reconciliation script. No Postgres HA.** — PITR does not protect against account compromise or a deleted database. The boxes keep the park selling through a cloud outage, so they are the real HA, and the money is better spent on the UPS. (rejected: Relying on PITR alone. Paying for HA before there is a second failure domain worth protecting.)
- **Package the agent as a signed tarball with separate runtime and app layers, installed into versioned directories with a `current` symlink and a small updater that health-checks and rolls back. No Docker on the box. No A/B OS OTA in Sprint 2; OS updates are a quarterly re-image rotated through the spare.** — Routine OTA drops to about 3 MB per box on metered cellular. Fewer moving parts suits a read-only root and a 4 GB Pi. With fewer than ten boxes, an OS OTA framework costs more than it saves. (rejected: Docker images (large pulls, more RAM, more failure modes). Mender or RAUC now (worth it at about 40 boxes). One monolithic tarball per release (about 50 MB per box per release).)
- **Roll out by channel (`dev`, `canary`, `stable`) with gates: staging fleet, bench Pi with hardware-in-the-loop tests, one production canary for 48 hours, then one branch at a time. Updates run before opening or when the station is idle, not 'at night'. The outbox event envelope is compatible forever, with cloud upcasters.** — Three artifacts deploy independently and boxes can be offline for weeks. Events are facts and must never be rejected for being old. Boxes without a UPS may be powered off overnight, so a night window may never occur. (rejected: Push-to-all updates. Rejecting sync from boxes below a minimum version (strands money-path data). A fixed overnight maintenance window.)
- **Keep fleet telemetry in Postgres (delta heartbeats, five-minute metric aggregates, error fingerprints). Logs stay on the box and are pulled on demand. Alerts go through the LINE Messaging API, email, in-app banners and an external uptime monitor.** — It fits a telemetry budget of roughly 20 MB per box per month and avoids running an observability stack for a fleet of tens. LINE Notify was discontinued in March 2025. The alerting runs inside the API, so something outside must watch the API. (rejected: Prometheus, Loki and Grafana. Streaming logs from boxes. LINE Notify.)
- **The cloud performs ACME DNS-01 on behalf of boxes (the box sends a CSR and receives a certificate). Prefer the router's static DNS entries to dnsmasq on two boxes, and specify a router that supports static DNS, VLANs, dual SIM and remote management.** — A DNS API token on every Pi in a mall can rewrite the zone if stolen. Brokered issuance keeps the token in the cloud and the private key on the box, and removes the custom Caddy build from the image. The router is already a single point of failure, so its DNS adds no new one, while box-hosted DNS adds two. (rejected: Caddy with a DNS provider module on every box (brief default). acme-dns (one more service to run). A shared wildcard certificate per branch (private key shared and transits the cloud).)
- **Use Ed25519 for staff tokens, booking QRs and booth vouchers. Keep HMAC only for wristband codes, with keys scoped per branch, rotated monthly with overlap, at least an 80-bit tag, and never distributed to booth boxes. Store private keys envelope-encrypted in the database under a master key held in the Render environment.** — Boxes never need to mint booking codes, so a symmetric key there is pure risk. Vouchers print on wide paper where code length is free. Wristbands are the one case where a short code matters for scan reliability, and a forged band is worth one day's admission. (rejected: One HMAC key on every box for bands, bookings and vouchers (brief default; one stolen booth box forges everything). Ed25519 on wristbands (the QR becomes too dense for a narrow curved band; worth a print test before ruling out finally).)
- **Test with one contract suite run against both the cloud and the box server, a property-based sync convergence harness with fake network and fake clocks, wire-level device emulators over a TCP transport abstraction, Playwright on WebKit and Chromium against a simulated box, and a nightly hardware-in-the-loop bench.** — These tests prove the two things that cannot be fixed cheaply in production: sync correctness on money and child release, and interchangeability of box and cloud transports. TCP-based emulators run on the Windows developer machine and in CI. (rejected: Interface-level simulators only (they validate the developer's assumptions, not the adapters' framing code). pty-based serial emulation (does not work on Windows). Testing sync by hand on staging.)
- **Merge the suite launcher-first: show every app as a tile and link out to legacy apps as they are, then add a signed single-sign-on handoff, then fold modules into the central database one at a time after the POS is live. Use one Postgres schema per module on a shared `core`, with legacy dumps landing in `legacy_<app>` staging schemas.** — The owner gets the professional launcher within weeks without merging anything. Working HR and scheduling software is not rewritten while the POS, which has no production system yet, waits. Schema-per-module avoids name collisions (`employee`, `role`, `item`, `transaction`) and keeps one pool and single-transaction integrity. (rejected: Big-bang merge of all apps into the monolith during Sprint 2. A separate database per app (breaks the central-database requirement and the pool rule). Everything in `public` (collisions and no ownership boundaries).)

## Risks
- [critical] Scope against capacity. 'All remaining software in one sprint' plus a suite merge is roughly 80 to 115 engineer-weeks by my de-duplication of the four recon maps' estimates. One long sprint with no gates removes the checkpoints that would catch drift. — MITIGATION: Keep it continuous but gate it into two-to-four-week milestones with demoable exits on staging. Deliver the launcher by federation first. Keep legacy apps running through POS cutover. Agree an explicit defer list: AI features, kiosk surface, stock purchasing, multi-operator features, OS-level OTA.
- [critical] Simulator-only delivery pushes all physical integration risk to the end: EDC serial protocols (the parity question is already open), the HX-X1 gate controller, TSPL printers, and iPad Safari reaching a LAN box over HTTPS with a public certificate. Simulators written from PDFs encode assumptions, not device behaviour. — MITIGATION: Run a non-blocking hardware spike track from week 1, one or two days per device, and turn captured bytes into emulator fixtures. Build wire-level emulators so real adapter code is tested. Stand up the bench early. Build a commissioning self-test into the agent.
- [critical] Sync correctness on money and child release: loss, duplication, reordering, clock skew, a crash between commit and ack on either side, and a cloud point-in-time restore that forgets events boxes were told were safe. — MITIGATION: Permanent `sync_event` ledger with entity-id idempotency. Per-box monotonic sequence. Cloud-owned ack cursor with 14-day retention of acknowledged events on the box. Property-based convergence harness with stated invariants, run on every pull request and nightly.
- [critical] Live authorisation defects sit under a system about to hold HR contracts and finance data. A branch manager can grant themselves `platform_admin` (`apps/api/src/routes/accounts.ts`). `GET /members/:id` and `GET /public/member-tier` do not filter by operator. `trustProxy` is unset, so the sign-in throttle becomes one global bucket on Render. — MITIGATION: Fix before anything else is built. Add delegation rules and target-operator checks. Add an authorisation matrix test generated from route and role definitions, and always seed two operators in tests.
- [high] Secrets and personal data on stealable Pis. The brief puts a shared HMAC key and a DNS API token on every box, and caches the operator's member base (children, allergy notes, pickup lists) on each. A stolen box is a PDPA breach with a 72-hour notification duty. — MITIGATION: Asymmetric signatures for cloud-issued codes; scoped, rotating HMAC for bands only and never on booths. Cloud-brokered ACME. LUKS on `/data` with the key in Pi OTP. Scoped member cache. Locked enclosures. Box revocation in the fleet console.
- [high] Version skew between the cloud API, the PWA and the box agent, which deploy independently, combined with boxes or spares that have been offline for weeks. — MITIGATION: Contract version advertised in the heartbeat. The PWA supports N and N-1. A deploy gate checks fleet versions per branch. The event envelope stays compatible forever, with upcasters and fixtures. SQLite migrations are additive only, so a rollback of one version is safe.
- [high] No UPS. Power loss can corrupt NVMe writes, leaves clocks wrong if the RTC battery is not fitted, and takes down both DNS-serving boxes at once. — MITIGATION: Make the UPS a go-live condition. Make the RTC battery a mandatory part. Put the outbox in its own SQLite file with WAL and `synchronous=FULL`. Rebuild a corrupt cache automatically; quarantine a corrupt outbox, never discard it. Persist a last-known-good clock. Document 'move the NVMe to the spare' as the recovery.
- [high] Metered cellular. PWA redeploys reach every iPad, a monolithic agent release is about 50 MB per box, the first member cache can be many megabytes, and iOS updates over park Wi-Fi can exhaust a capped SIM. — MITIGATION: Split the agent into runtime and app layers. Use deploy windows during stabilisation. Bootstrap caches on the bench. Compress sync batches. Send delta heartbeats. Defer iOS updates by MDM or router rules. Track data use per box.
- [high] A single 1 CPU API instance carries REST, sockets, jobs and static files. The POS inactivity lock signs out fully every two minutes (`apps/pos/src/auth/OperatorContext.tsx`), which forces a new argon2 sign-in on every unlock. `apps/api/src/index.ts` has no graceful shutdown, and Render health-checking `/ready` would restart the API on a database blip. — MITIGATION: Make the lock local and keep the token. Add SIGTERM handling. Point Render at `/health`. Use jittered reconnects. Use process roles so jobs can be split out. Run a small load test of 20 tills plus 40 syncing boxes plus a rollup.
- [high] Connection pool starvation once transactions are introduced. `packages/db/src/index.ts` sets no pool limits or timeouts, and a transaction held across a 2C2P or SMS call pins a connection. — MITIGATION: Configure the pool and role-level timeouts. Forbid network I/O inside transactions and use an outbox table with jobs. Publish a connection budget.
- [high] Handling of the production dump and personal data. The working copy is inside a OneDrive-synced folder, so a dump saved there would upload to Microsoft's cloud. The legacy system includes face enrolment (SCRUM-118), which the brief forbids. Staging must not hold real children's or HR data. — MITIGATION: Move the repo out of OneDrive (this also avoids pnpm link and file-lock problems). Keep dumps on an encrypted volume outside any synced folder and outside git. Write an anonymising scrub script before any staging restore. Explicitly exclude biometric tables and identity-document images from the migration.
- [high] Unknown state of the Replit apps. Some may be UI on mock data, as `oto-till` was, so 'import' could mean building backends from scratch. They will bring colliding table names and their own role systems, and may contain committed secrets. — MITIGATION: Quarantine raw imports outside the workspace. Run a per-app inventory (real backend or mocks, schema, users, data volume, production use) before sizing. Scan with gitleaks. Use schema-per-module and legacy staging schemas. Follow a strangler order starting with people and org.
- [high] A remote developer with hardware in Phuket, and a bus factor of one. EDC terminals are tied to the SCB merchant and cannot be duplicated abroad. — MITIGATION: Duplicate bench kit for everything except EDC. An on-demand, audited support tunnel. A named on-site technician following the commissioning self-test. Client-owned accounts with a break-glass document.
- [medium] Events from different boxes arrive out of causal order: the gate reports a passage for a band whose sale has not synced yet, or a sale references a member created offline that is later merged. — MITIGATION: Event tables use soft references with a reconciler, and no hard foreign keys across boxes. Add `member_alias` with `merged_into_id`. Change the `child` cascade to restrict. The convergence harness asserts that delivery order does not change the final state.
- [medium] Late offline events invalidate closed-day rollups, end-of-day cash counts and settlement exports. — MITIGATION: A dirty-day recompute mechanism. Reports disclose late events. Settlement is keyed by terminal id and batch, not by date alone. End-of-day shows unsynced boxes before it allows a close.
- [medium] Partitioning and trigger pitfalls. Drizzle Kit models neither partitions nor triggers and may try to undo them. Unique constraints on a partitioned table must include the partition key. `updated_at` is set only in application code, so other writers and the migration will not bump it. — MITIGATION: Hand-written SQL migrations, with the affected tables excluded from the generator. Dedupe in the ledger. A database trigger for `row_version` on every cacheable table. A DEFAULT partition plus a monitor job.
- [medium] Alert fatigue, and the alerting system being hosted on the service it monitors. Boxes that are switched off overnight would page someone every evening. — MITIGATION: Rules aware of opening hours, flap suppression, severity tiers, an external uptime monitor, and till header status chips as the first-line signal.
- [medium] Booth boxes sit on a network the park does not control. Input is a USB HID keyboard and the printer is on the LAN. — MITIGATION: USB printer or an isolated travel router. A kiosk compositor with VT switching disabled. A udev allow-list for the button's VID and PID. No band keys or member cache on booths. Vouchers signed per box.
- [medium] Certificates and naming. Let's Encrypt lifetimes are shrinking, certificate transparency logs publish every box hostname, and some resolvers filter public names that resolve to private addresses. — MITIGATION: Renew at two-thirds of lifetime and alert below 21 days. Use opaque hostnames. Serve box names from the router's static DNS. Consider a dedicated cheap domain for boxes.
- [medium] Unmanaged iPads: surprise iOS updates, service-worker cache eviction, the local-network prompt, and Safari-specific behaviour that Playwright's WebKit does not fully reproduce. — MITIGATION: Apple Business Manager plus a light MDM. A box-served copy of the POS shell as an emergency URL. A real-iPad manual checklist per release.
- [low] Hosting Thai personal data in Singapore, and LLM features sending staff or customer text to a third party. — MITIGATION: State hosting and processors in the privacy notice. Get the owner's PDPA adviser to confirm. Defer AI features until after cutover and choose a provider with a no-training data policy.
- [low] Render plan names and prices have changed over time, and the brief's '1 CPU / 2 GB' tier may not map to a current plan with PITR. — MITIGATION: Verify the plan matrix and the PITR window before budgeting. Size by measured load after the first migration trial.

## Disagreements with brief
- **One continuous sprint for everything (section 2), now plus the suite merge.** This is a programme of many months. Run it continuously if you wish, but with gated milestones every two to four weeks and an agreed defer list. Without gates, nothing catches drift on the money path.
- **Nothing touches hardware until stabilisation (section 2).** The adapter-and-simulator rule is right, but leaving every physical unknown to the end is the biggest schedule risk in the brief. Run small parallel hardware spikes from week 1 and feed captured bytes into the emulators. This blocks nothing.
- **A band and booking HMAC key 'every box holds' (section 8).** One stolen booth box could forge bookings and vouchers for every branch. Sign cloud-issued booking QRs with Ed25519 so boxes hold only a public key. Sign vouchers with the booth's own certified key. Keep HMAC for wristbands only, scoped per branch, rotated monthly, and never on booths.
- **Caddy with a DNS provider module on every box (section 6).** That puts a DNS API token on every Pi in a mall. Let the cloud run ACME DNS-01 on the box's behalf: the box sends a CSR and receives a certificate. The token stays in the cloud, the private key stays on the box, and the custom Caddy build leaves the image. The '90 days, so an outage never invalidates' comfort margin will also shrink as Let's Encrypt shortens lifetimes (verify the current schedule).
- **dnsmasq on two boxes as the park's DNS (section 6).** It adds two failure points that both go down in a power cut. Use the router's static DNS entries, and choose a router that supports them along with VLANs, dual SIM and remote management. Fall back to box-hosted DNS only if the router cannot do it.
- **The box cache holds 'members and children' for the whole operator (section 4).** Members are operator-wide, so every Pi would carry every child's name, allergy notes and pickup list. Cache by branch recency plus active bookings and wallets, look up the rest online, and rely on the offline create-then-merge rule that is already required. Booths cache no members.
- **Audit 'archived after twelve months' (section 9).** Financial and child-release audit should be retained for at least five years, pending the accountant's confirmation. Archive cold partitions to object storage; do not delete them.

- [medium] Partitioning audit_log now is over-engineering for this volume, and the stated reason to hurry is wrong.
