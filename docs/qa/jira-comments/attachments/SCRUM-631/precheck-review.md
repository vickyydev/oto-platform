## Findings requiring correction before execution

### P1 - medium - the readiness log window can omit its own successful result

The readiness start branch writes `intent.at` before submitting the Render job, but writes `intent.job.startedAt` with a new timestamp only after the jobs POST returns. Collection uses the latter timestamp as the Render log query's `startTime`. A small metadata job can connect, print its only `SCRUM631_READINESS=` line and finish before the creation request returns; that line then predates the collector's lower bound. The job may be succeeded while every collect attempt fails `READINESS_LOG_REQUIRED`.

Fix: use the durable intent timestamp captured before dispatch as the log-window lower bound, and preserve that timestamp in the job binding. Keep the exact job/resource filter; do not solve this by collecting unrelated service logs or by rerunning an uncertain job. This finding is established by source ordering, not a staging reproduction.

### P2 - medium - the readiness job lacks the required full release binding

The census independently reads the supplied CI run and all three latest deployment identities, then calls the reviewed `validateRelease`, which enforces six green jobs and exact same-source API/Admin/OTO deployments. The readiness helper accepts only a SHA argument, checks the latest API deployment, and can submit the job while CI is red/running or Admin/OTO are old. This is an external one-off job, so the required green-and-live precondition must hold before its dispatch as well.

Fix: pass the same concrete release plan to readiness, validate the ticket/SHA/run and three expected service identities, and perform the same six-green/latest-three-live validation before the start branch submits its job. Persist those exact release bindings in the intent. Collection must check the original intent/job/service/deployment binding, rather than stamping whichever latest API deployment happens to be live at collection time. A final same-binding check before publishing the successful metadata receipt prevents a deployment race from being described as one exact checked deployment. The coordinator may already gate calls externally, but these current helper bytes do not enforce or record that gate themselves.
