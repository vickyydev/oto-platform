# UNDERSTANDING

## auth-permissions
Sprint 1 auth is a working single-app, cloud-only design. Sign-in is phone + argon2 password. The session is an opaque 32-byte token in a host-only httpOnly cookie, stored SHA-256-hashed in a `session` row and looked up in the database on every request. Permissions are 28 compile-time `service:resource:action` strings bundled into 5 seeded system roles. They are resolved as a pure union across scoped role assignments. Audit is one insert helper. Idempotency is an (account_id, key) response cache that only works for cookie-authenticated requests.

None of this is wrong for the cloud half of the brief, and the opaque cookie should be kept for instant revocation. It contains nothing for the box half or the suite half.

**Missing for the boxes**
- There is no signed token, signing key or JWKS, so a box cannot verify a session offline.
- There is no device or box principal. `station.deviceKeyHash` exists but no route reads it, and `session.stationId` is never written.
- Audit has no occurred-at, origin or station fields.
- Idempotency cannot be used by a device: `account_id` is NOT NULL and the plugin requires `req.auth`.
- Idempotency also caches 5xx responses and wedges on a crashed in-flight request, which would poison a retrying outbound queue.
- IDs are UUIDv7 "so they stay client-generatable", but no route accepts a client-supplied id. The one replay-safe mechanism the brief asks for ("idempotent by ID") is therefore not wired.

**Missing for the launcher and module-aware permissions**
- There is no module registry and no module entitlement.
- There is no role CRUD, no per-account override and no deny semantics.
- System-role permissions are never re-synced after the first seed.
- The POS collapses the whole permission list into a manager/staff boolean.

**Live defects to fix before building on this**
- Role assignment has no delegation guard: a branch manager can grant themselves `platform_admin`.
- `trustProxy` is unset, so on Render the per-IP sign-in throttle becomes one global bucket.
- No handler uses a DB transaction, so audit rows are not atomic with the change, although the comments say they are.
- The inactivity lock deletes the server session, which contradicts "offline unlock verifies the existing token".

**Recommended shape**
- Keep the cookie session for the cloud and mount all apps on one origin, so SSO is "same cookie" plus a `GET /me/apps` endpoint.
- Add an Ed25519-signed shift token minted from that session for the box channel.
- Add a device-authenticated `/sync` ingest with entity-ID idempotency, stamping `occurred_at`, `recorded_at` and station.

Nothing was run. The 5xx-caching and single-bucket-throttle items are inferred from code reading, not reproduced.

### Gaps
- No signed staff token, signing keys, JWKS distribution or revocation feed. Sessions are opaque and verifiable only against Postgres (plugins/session.ts). — IMPACT: Blocks brief sections 4 and 8: 'Verifies staff session tokens offline with a public key'. Without it a box cannot authorise a till action, a gate override or a child release when the internet is down. This gates box-agent core, item 1 of the Sprint 2 execution shape. — EFFORT: Medium, about 4-6 dev-days. Covers the Ed25519 key table with rotation, the /auth/station-token mint endpoint, moving the permission evaluator to packages/shared, a verify library for the agent, the revocation push, and tests including clock skew.
- No device or box principal. AuthContext is account-only. There is no `box` table, station.device_key_hash is unused, no station routes exist, session.station_id is never set, the stationKind enum lacks 'booth', and there is no device-session model for kiosk, booth or customer display. — IMPACT: Boxes cannot register, send heartbeats, open the outbound WebSocket or submit their queue. The brief's 'one active till per station, one customer display, read-only observers' cannot be enforced. The booth's 'QR badge or PIN' staff sign-in and the SCRUM-116/117 reception-kiosk activation have nothing to build on. The customer display still rides the till's cookie (decision D8). — EFFORT: Large, about 8-12 dev-days. - Idempotency cannot serve a box outbound queue. It requires a cookie session, account_id is NOT NULL, the TTL is 24 hours, it caches 5xx responses, a crash leaves a permanent IN_FLIGHT row, the claim is non-atomic, and the hash is order-sensitive. No route accepts client-minted IDs, and business-key conflicts reject with MEMBER_EXISTS and do not merge. — IMPACT: Replayed offline sales, payments, bands and releases would be rejected with 401, wedged with a cached 500 or IN_FLIGHT, or duplicated after TTL expiry or re-execution with fresh server IDs. This breaks 'Every item idempotent by ID' and 'same phone created at two counters merges'. It is a data-integrity risk on money and on child release. — EFFORT: Large, about 8-10 dev-days. - Audit has no occurred_at, origin, station or box, actor_type, auth_method or source_event_id. Replays would double-log. Child-release and cash-variance investigations need the true event time and station. Merging the HR 'activity logbook' (SCRUM-168) into one log is not possible without an actor and origin model. — EFFORT: Small to medium, about 2-3 dev-days, plus about 1 day for monthly partitioning, which needs a composite PK with created_at.
- No DB transactions anywhere in apps/api. Audit rows are separate autocommit statements, and the write logic lives in route handlers, not in services. This contradicts audit.ts and CLAUDE.md section 3. — IMPACT: Partial writes on a crash: for example the tier changes but no audit row is written, or an account exists with no roles. The offline sync ingest and the HTTP routes cannot share one write path. Every new module from the Replit import would copy the pattern. — EFFORT: Medium, about 4-5 dev-days to extract member, visit, account and catalog services taking a tx handle. This is mechanical work and needs good test coverage; tests already exist for the affected routes.
- Privilege escalation: holding admin:role:assign at any scope allows granting any role, including platform_admin, at any scope to any account id. There is no operator check on :id and no delegation rule (routes/accounts.ts POST /:id/role-assignments and POST /). — IMPACT: A branch manager can grant themselves platform-wide admin. This becomes critical once the same permission service guards HR contracts, finance (Satang) and customer inbox data in one central system. Fix it before centralising. — EFFORT: Small, about 1-2 dev-days. The granter's coverage must include the granted scope, the platform role must be restricted to platform admins, target-account operator checks must be added, and tests written.
- No module registry, module entitlement, custom roles, per-account overrides or deny semantics. role_name_unique is global. There is no role CRUD. The seed never re-syncs role bundles. The POS uses a manager/staff boolean. — IMPACT: This is the client's explicit Sprint 1 review request: central, module-aware access with switches for pages and features. Without it each imported app (OTO App HR and scheduling, Analytics, Satang, Inbox, Radar, Wheel) would bring its own role system, and the launcher cannot know which tiles to show. New permission strings will not reach existing databases. — EFFORT: Large, about 10-15 dev-days. Covers manifests and the registry, 3-4 tables with migrations, the evaluator change with tests, role-matrix and override admin UI, a system-role sync step, a front-end can() hook, and GET /me/apps. Add mapping of legacy roles from the production dump, which cannot be sized until the dump is seen.
- No launcher or SSO surface. Sign-in UI is embedded in the POS LockScreen, GET /me returns no app list, no production hosting topology is defined (no CORS, no trustProxy, COOKIE_SECURE defaults to false), and there is no decision yet between path-mounted apps and subdomains. — IMPACT: The addendum's headline requirement, one sign-in then pick an app you have access to, has no home. Choosing subdomains later forces a cookie-domain or OIDC rework and exposes the session to the marketing-site and box hostnames under the same registrable domain. — EFFORT: Medium, about 4-6 dev-days for a single-origin launcher shell, a shared auth package, GET /me/apps and production cookie and proxy hardening. A central OIDC-style auth service for subdomains would be 10+ days.
- The POS lock deletes the server session: OperatorContext logout() calls signOut on the inactivity timeout. There is no unlock endpoint and no offline password or PIN verifier. — IMPACT: This contradicts brief section 5 ('Offline unlock verifies the existing token'). With 2-minute locks, every unlock offline would be a fresh sign-in, which is the unresolved open question. Online, it creates a new session row and an argon2 verify on the cloud every 2 minutes per till. This is wasteful on the 1 CPU API tier the brief specifies for Render. — EFFORT: Small to medium, about 2-3 dev-days. Covers a client-side lock that keeps the token, POST /auth/unlock, a box-side verifier, and an owner decision on password hash versus PIN on the box.
- The sign-in throttle is in-memory and keyed on req.ip with trustProxy unset. findAccountByPhone ignores the operator. — IMPACT: On Render all clients share one IP bucket, so 20 bad attempts lock every sign-in for 5 minutes across all apps once the launcher is the single door. The same phone under two operators signs into an arbitrary tenant, which matters when the production dump is merged or a second operator is added. — EFFORT: Small, about 1-2 dev-days. Set trustProxy, throttle by phone plus device or box id, store buckets in Postgres, and decide between a global identity with operator memberships and the current per-operator account. The identity decision itself is design work with migration consequences.
- Account and credential model is not ready for the merged suite. The only credential is a password, hashing is argon2-only, password reset requires phoneVerifiedAt, and there is no mapping strategy for legacy users in the production Postgres dump to employee, account and role_assignment. — IMPACT: Staff from the existing OTO App cannot sign in after the merge unless they are forced through SMS setup or reset. That incurs SMS cost and cutover friction for every employee. The alternative is a multi-algorithm verifier with rehash on login. Booth, kiosk and timekeeping need PIN or badge credentials, and face-ID (SCRUM-118) is excluded by the brief. — EFFORT: Medium, about 3-5 dev-days after the dump is profiled. Covers a credential table for password, pin and badge, a legacy-hash verifier or a bulk invite flow, and the import mapping.
- Unauthenticated mutations have no idempotency. POST /public/bookings ignores the Idempotency-Key the POS sends, and the booking reference is random. — IMPACT: A double submit or retry from the booking site or kiosk creates duplicate bookings. Once 2C2P Redirect payments are attached, this could mean duplicate charges or reconciliation orphans. — EFFORT: Small, about 1 dev-day. Allow a public principal keyed by key plus client fingerprint or a client-minted booking id with ON CONFLICT.

## db-schema
The Sprint 1 Drizzle schema (37 tables, 7 enums, all in Postgres `public`, 3 migrations) is a sound foundation for identity, members and catalog, but it is cloud-CRUD shaped. It is not yet sync, ledger or suite shaped. This was a read-only review; nothing was run or changed.

**What already fits**
- IDs are UUIDv7 `uuid` primary keys generated in the application by one `newId()` and never by the database, so a box can mint them with no schema change.
- Money is integer satang, time is `timestamptz`, and soft-delete and audit conventions exist.
- A generic role / permission-string / scoped-assignment model exists.

**What is missing**
- **Incremental sync.** No table has a version or change-sequence column. `updated_at` is set only by Drizzle's client-side `$onUpdate`, with no database trigger. Several tables the box must cache are hard-deleted (`role_assignment`, `branch_holiday`) or have no `archived_at` and no `updated_at` (`role_permission`). Deletions and revocations can therefore never reach a SQLite cache.
- **Box and device model.** There is only a flat `station` table (branch, name, kind, `device_key_hash`, `last_seen_at`) with no API route using it. There is no box table, device inventory, station-to-device assignment, heartbeat, config version, or booth role. `session.station_id` is a bare uuid with no foreign key.
- **Money path.** `transaction`, `transaction_line`, `payment`, `wallet`, `wallet_entry`, `wristband`, `item` and the two stock tables are jsonb-payload placeholders that no API code reads or writes.
  - They lack `station_id`, receipt and tax-invoice numbers, origin and received timestamps, tax/discount/service-charge columns, EDC and 2C2P fields, refund and void linkage, and cash sessions.
  - `wallet` is keyed to `member` with a mutable balance. The prototype and the brief put the wallet on the child's wristband.
- **Suite merge.** Everything lives in one `public` schema with generic table names (`employee`, `department`, `role`, `item`, `account`, `transaction`). These will collide with the imported HR, asset and finance domains.
  - The role model has a global-unique role name, no module registry, and no per-role or per-account feature switches. The client's Sprint 1 feedback asks for exactly those.

**Recommendation.** Before Sprint 2 builds on the schema:
- Add a change-sequence and tombstone convention.
- Build the box/device model.
- Rewrite `future.ts` as a real append-only ledger with station-scoped numbering.
- Move to Postgres schema-per-module on a shared core (tenancy, identity, RBAC, audit, files) inside one database and one pool.

### Gaps
- There is no change-sequence or version column and no tombstones, so incremental sync to the box SQLite cache cannot be built safely. `updated_at` is set only by the application (Drizzle $onUpdate, no trigger, millisecond precision). role_assignment and branch_holiday are hard-deleted. role_permission has no timestamps. Most cacheable tables (department, role, tax_override, branch_tax_config, station, account) have no archived_at. — IMPACT: High. A box pulling rows where updated_at is newer than its cursor will miss rows committed out of order, rows written by other apps or by the migration, and every deletion. The worst case is a revoked role assignment or a deactivated staff account that stays valid on an offline box. That is a security defect, not only a data-freshness one. The problem grows once HR and ops modules write employee and account rows from their own code paths. — EFFORT: Medium, about 3 to 5 days. Add a `row_version bigint` fed by one global sequence, or a per-operator `change_seq`, maintained by a BEFORE INSERT/UPDATE trigger on every cacheable table. Convert the hard deletes to archived_at or revoked_at. Alternatively, add a generic `sync_change` feed table (seq, operator_id, branch_id, table, row_id, op) written by a trigger. The box then pulls rows with seq greater than its cursor, per branch. Drizzle's migration generator does not manage triggers, so they need hand-written SQL migrations.
- The box, station and device-assignment model is missing. Only a flat `station` table exists, holding device_key_hash on the station itself. Required tables: `box` (operator, branch, device key hash or public key, role, hostname, LAN address/DNS name, image and agent version, status, last_seen_at, registered_at, revoked_at); `box_heartbeat` or a latest-status jsonb (printer reachability, paper status, USB devices present, last sync, queue depth); `device` as reported by the box (box_id, type, transport usb/lan/serial, address or port, model, serial or TID, last_seen); `station.box_id`, where a station belongs to exactly one box and a box hosts many stations; `station_device_assignment` with slots receipt_printer, kids_band_printer, adult_band_printer, kitchen and bar printer, scanner plus scanner_mode camera/ipad-bt/box, card_terminal, and a payment-method-to-device routing map; a station config_version for pushing config to the box; a receipt prefix per station; an active-till lease (one active till per station, one display, read-only observers); booth config (layout, prizes, probabilities, screensaver, staff assignment). The station_kind enum lacks booth and F&B kinds. session.station_id has no FK. — IMPACT: High. This is the first item of the Sprint 2 execution shape (box agent core: registration, heartbeat, station model). The station setup wizard's new 'choose the box' step and its 'devices offered are those the box reported' rule have no backing store. EDC routing by payment method (card to the NEXGO, QR to the PAX) and per-terminal settlement export keyed by TID need device rows that carry the TID. — EFFORT: Medium, about 4 to 6 days for schema plus CRUD and registration endpoints. Moving device_key_hash from station to box is trivial now, because only one seeded row exists and no API code uses the table. Replace the pg enum with text plus CHECK, or a lookup table, to avoid a migration every time a new station kind is added.
- The sales ledger is a set of placeholder tables, not an append-only, offline-originated ledger. `transaction`, `transaction_line` and `payment` lack: station_id, box_id and shift or cash-session link; a receipt number and a tax-invoice number with a per-station prefix and a unique index on (branch, station, number); `occurred_at` (the box clock) versus `received_at` (the cloud), and an origin flag online or offline; first-class columns for subtotal, discount, service charge, VAT and tax breakdown, because historical calculations must never be recomputed (SCRUM-61); line-to-product, line-to-package and line-to-tier snapshots; refund, void and credit-note linkage by reference to the original instead of mutation (SCRUM-51); on payment, the terminal TID and MID, approval code, masked card, provider transaction id, the 12-character GHL pos_ref_no, the Digio 6-digit rolling reference, the 2C2P invoice number, inquiry and unknown-outcome state, settlement batch, and raw-byte log storage. Status fields are mutable free text with default 'draft'. — IMPACT: High. This is the money path. Without per-station numbering, two offline tills collide on receipt numbers, which the brief flags as a Thai tax compliance concern pending the accountant's prefix scheme. Without structured columns, settlement reconciliation against SCB and 2C2P (SCRUM-102, brief section 10) turns into jsonb scraping. Drafts should live on the box only. The cloud should only ever receive finalised, immutable documents inserted idempotently by primary key (ON CONFLICT DO NOTHING). — EFFORT: Large, about 1.5 to 2.5 weeks for the schema and the ingest service. There is nothing to migrate, because the tables are unused and empty. future.ts should be rewritten, not extended. Include `cash_session` and `cash_movement` (opening float, paid-outs, safe drops, close count and variance) and `settlement_batch`. The receipt-sequence design is either a per-station counter held on the box and persisted in SQLite with a range lease from the cloud, or prefix plus a monotonic local counter; the choice is blocked on the accountant's answer. Build the unique index and columns now, with a configurable format.
- The wallet model conflicts with the prototype and with the offline rules. The wallet is keyed to the member and carries a mutable balance_satang. The prototype and the brief put stored value on the child's wristband, with a ledger. wallet_entry has no station_id, account_id, transaction_id, idempotent client id semantics, expiry (SCRUM-91 expire and reactivate), or offline flag. There is no configurable offline spend cap and no meal-credit representation (SCRUM-89). — IMPACT: High. It is financial liability data, and it is the one area the brief says is not made safe offline by design. If the balance stays a mutable column, offline spends from two stations cannot be reconciled. The ledger must be the truth and the balance a projection recomputed in the cloud. An overdraft arising from the capped offline spend must be recorded, not rejected. The wallet-liability report (SCRUM-99) depends on this. — EFFORT: Medium, about 4 to 6 days. First decide the wallet owner (child, band, member, or a wallet with multiple lookup keys as in the prototype's code plus qrCode). This also determines how the production dump's balances are mapped.
- Wristband, band-code, signed-token and gate tables are inadequate or missing. `wristband.code` is not unique. There is no link to child, member, visit or transaction. There is no valid_from or valid_until, no issuing station, and no signature key id. Missing entirely: a signing-key registry with rotation (the HMAC key every box holds, and the staff-token public keys); `passage_event` (append-only, from gate serial: direction, outcome, tailgating); occupancy projection; an anti-passback state sync; `booking_redemption` (single-use log, box-originated); `voucher`, `spin` and `voucher_redemption` for the booth. — IMPACT: High for the Arrival and Booth execution blocks. Signed-code verification offline depends on key distribution and rotation being modelled. Without a redemption log that accepts box-originated rows and flags double redemption after the fact, the single-use rule cannot even be audited. — EFFORT: Medium to large, about 1 to 1.5 weeks. All of these fit one pattern: an append-only event table with a box-minted UUIDv7 primary key plus station_id, occurred_at, received_at and an idempotent insert. Define that pattern once, as a helper in helpers.ts.
- Child supervision and release tables do not exist. Needed: authorised pickup persons per child, check-in and check-out records, release evidence (staff, time, collector, evidence), supervision rules and nanny assignment (SCRUM-74 to 79). The `visit` and `visit_child` tables have no station or origin columns either. — IMPACT: High. Offline child release is mandatory in the brief: 'A child is never refused release'. The authorised-pickup list must be in the box cache set, so it needs the same change-sequence treatment. Release records are safety-critical, append-only, box-originated events. — EFFORT: Medium, about 4 to 5 days of schema. PDPA applies: no identity-document photos. Pickup-person photos need an explicit decision.
- Idempotency and audit assume a human account calling the cloud. idempotency_key has PK (account_id, key) with account_id NOT NULL, and a 24-hour TTL. audit_log has no station, box or source column, and no occurred_at distinct from created_at. — IMPACT: Medium to high. A box replaying a queue after a multi-day outage, or replaying items originated by several staff, either re-executes after the TTL expires or cannot authenticate as an account at all. Entity-level idempotency by primary key is the real safeguard for queued events. Insert on the box-minted id with ON CONFLICT DO NOTHING; that makes the header mechanism secondary. Audit rows for offline actions need the box-side time and the staff id taken from the signed token, not from the request session. — EFFORT: Small to medium, about 2 to 3 days. Add a device principal (box_id) to the auth context. Add an ingest endpoint that upserts by primary key. Add station_id, box_id, source and occurred_at to audit_log. Plan monthly partitioning of audit_log now; it is cheap before data exists and painful once it does.
- Member merge is not modelled. The unique (operator_id, phone) index plus the 409 MEMBER_EXISTS response is correct for online use, but the brief requires the same phone created offline at two counters to merge. There is no member_alias, merged_into_id or remap table. child cascades on member delete. — IMPACT: Medium. Offline-created members carry box-minted ids that children, visits and sales already reference by the time they sync. Without an alias or remap record, those rows fail their FK or end up orphaned. The same mechanism is needed for deduplication during the production-dump migration (SCRUM-12 profiles duplicate customers). — EFFORT: Small to medium, about 2 to 3 days. Add `member.merged_into_id` plus a `member_alias(old_id, member_id)` table, and a server-side sync rule that rewrites FKs on ingest. Change the child FK from ON DELETE CASCADE to restrict.
- RBAC is not module-aware, and there are no feature switches. role_name_unique is a global unique index on name alone. Permissions are a hard-coded TypeScript list covering only admin, pos and catalog. There is no `module` or `app` registry, no operator_module enablement, no role or account level page and feature toggles, no launcher tile metadata, and no re-seed path for new permissions into existing databases. The platform_admin cross-tenant flag that a code comment refers to does not exist as a column. — IMPACT: High for the addendum. The launcher ('pick an app you have access to') and the client's explicit Sprint 1 feedback both depend on it. Every imported app (OTO App HR, Analytics, Satang, Asset Manager, Radar, Wheel) needs to register its permission namespace and have it appear in one central admin UI. — EFFORT: Medium, about 1 week. Add `app_module` (key, name, icon, route, sort order, status), `operator_module` (enabled per tenant or branch), a `permission` catalog table synced from code on deploy by an idempotent upsert instead of seed-once, `feature_flag` with role and account overrides, and change the role unique index to (operator_id, name) with a partial unique index for system roles. Existing role_permission and role_assignment rows stay valid.
- A single `public` schema with generic table names will not absorb the suite cleanly. employee, department, role, account, session, item, transaction, payment, booking and attendee already occupy names the imported apps almost certainly use. The `employee` table is a stub with 6 business columns, against the X5 and X6 needs of contracts, e-signature, org chart, reviews, leave, rotas and timekeeping. The account login is phone-only. — IMPACT: High for the merge, but it is cheap to fix now. Recommendation: one database, one connection pool, and a Postgres schema per module via Drizzle pgSchema. `core` would hold operator, branch, department, employee identity, account, RBAC, modules, audit, files, idempotency and sync. `pos` would hold members, catalog, sales, wallets, bands, stations, boxes and devices. Further schemas: `hr`, `sched`, `ops` (tasks, checklists, announcements, SOP, fix), `events`, `inventory`, `msg`, `booth`, and `analytics` (rollups and materialised views only, with no foreign ownership). Rules: cross-schema FKs are allowed only INTO core, and sometimes into pos.member. Modules never FK each other's internals. Each module owns its own migrations folder. Legacy dumps land first in a `legacy_<app>` staging schema and are transformed from there; the transform is never run against production. This keeps single-transaction integrity and one pool (brief section 9), while giving collision-free names, per-module grants and clear ownership. Schema-per-tenant remains rejected, as ARCHITECTURE.md already states. A separate database per app would break the central-database requirement and the one-pool constraint. — EFFORT: Medium, about 3 to 5 days to restructure now. There are 37 tables, only a seeded dev database and no production data yet; the change is `ALTER TABLE ... SET SCHEMA` plus Drizzle pgSchema definitions, and a multi-schema drizzle-kit config through schemaFilter. The cost rises sharply once Sprint 2 tables and the migrated production data exist. The real domain modelling of HR, scheduling and ops is large, measured in weeks. It cannot be sized until the Replit apps and the production dump are shared.
- Staff identity is not ready for offline token verification or for unification across the suite. Sessions are opaque, database-backed and cookie-based, which a box cannot verify, and no table holds signing keys, PIN hashes or QR-badge credentials. Booth staff are meant to sign in by QR badge or PIN, and the open question on offline sign-in covers staff seen on that box in the last 30 days. employee and account are split in two tables, with a nullable link between them. — IMPACT: Medium to high. The box cache must contain staff accounts, roles and a verifier: an argon2 hash for offline unlock, or a PIN hash. Putting password hashes on a Pi in a mall is a security decision that needs explicit sign-off, and a separate short-PIN credential is the safer choice. Imported apps will bring their own user tables, which must map onto core.account and core.employee. Reconciling identities between phone-keyed accounts and whatever keys the legacy apps use is a migration risk. — EFFORT: Medium, about 4 to 6 days. Add signing_key (kid, public key, purpose, rotated_at), account_credential (type pin or badge, hash), and box_known_staff (or derive it from the sync scope). Add email or an external-id column on account for legacy identity mapping.
- There is no migration staging or provenance. No table carries legacy_id or source_system columns, and there is no id-mapping table. The only hook is member.created_via, which includes 'import'. — IMPACT: Medium. SCRUM-12 and brief section 12 require a repeatable migration, reconciled by counts and totals until two runs match. With multiple source apps merging, every migrated row needs (source_system, source_pk) provenance to stay idempotent across re-runs and to debug reconciliation. — EFFORT: Small, about 1 to 2 days for a generic `core.legacy_map(source_system, source_table, source_pk, target_table, target_id)` plus the staging-schema convention. The transforms themselves cannot be sized until the dump arrives.
- Small hygiene issues that become expensive later. (1) /public/member-tier does not filter by operator. (2) status and kind columns across future.ts are unconstrained free text. (3) wristband.code and tax_override (branch, category, product) lack unique indexes. (4) member.tier_code is a soft reference. (5) product.price_satang is integer while the ledger uses bigint. (6) the seed is insert-once, so permission and role bundle changes never reach existing databases. (7) there is no operator_id on branch-scoped tables such as station, branch_holiday, tax_override and stock_location, which forces a join in every sync-scope query and in any future RLS policy. — IMPACT: Low to medium individually. Item (1) is a cross-tenant data leak once a second operator exists. Item (7) complicates per-operator or per-branch sync filters, and rules out simple RLS as defence-in-depth when many modules share the database. — EFFORT: Small, about 2 to 3 days in total. Consider denormalising operator_id, and branch_id where relevant, onto every tenant-owned table as a schema rule, so that sync scoping and optional RLS become uniform.

## pos-frontend
The POS frontend in `oto-platform/apps/pos` is still mostly the Replit prototype running on in-memory mocks. Only a thin slice talks to the real Sprint 1 API.

**What is real and what is mock**
- The real HTTP layer is small: `api/client.ts` (57 lines, one `fetch`) plus about 50 typed wrappers in `api/platform.ts`. Only 13 files import it.
- `mockApi.ts` (5,837 lines) exports about 133 of its own functions and re-exports about 69 functions from `store/catalogStore.ts`, which has 84 exports in total. 80 files import it.
- Every mock function is synchronous. A grep for `async` or `Promise` in `mockApi.ts` and `catalogStore.ts` finds nothing.

**Transport-agnostic data layer (LAN box or cloud)**
- The network client itself is easy to change: it is one file with a hardcoded `/api` prefix.
- The rest is hard, for five reasons:
  - Auth is a same-origin httpOnly cookie, which cannot reach a box on another origin. The brief requires signed bearer tokens the box can verify offline.
  - Sale building, totals, band and wallet minting, stock guards and end-of-day all run in the browser. They use float baht and `Math.random` ids.
  - 80 files of synchronous call sites would have to become asynchronous commands.
  - Idempotency keys are generated at call time inside the wrappers, so a queued retry gets a new key.
  - There is no endpoint resolver, health probe or online/offline state.
- The existing `catalogStore` + `hydrateFromApi` pattern is the right seam for read data. Writes need a new command layer.

**Split-screen till and customer display**
- Today it is plain React props and callbacks inside one component tree. `Till.tsx` holds about 30 `useState` hooks and passes `liveSale`, `customerStage` and the draft fields down to the customer-facing panes. The same pattern is copied into five other host surfaces.
- The one API-mediated piece is `stagePendingLookup` / `consumePendingLookup`. The till calls both back-to-back on the staff session, so it is not a real two-device channel.
- Making the display a separate physical device needs:
  - a serialisable per-station sale session document owned by the box;
  - a push channel (WebSocket or SSE);
  - a `/display` route with device pairing;
  - the pane components refactored to take `{state, dispatch}`.

**Station setup wizard**
- It models a per-iPad profile that lives only in React state and is lost on reload. The profile holds a name, capabilities, five printer ids and a scanner mode.
- Devices come from a branch-wide seeded device list.
- It has no box concept, no box-reported devices, no card terminal or payment-method routing, no server persistence and no role gate on the route. Test print and test scan are toasts.

**PWA and other groundwork**
- There is none: no manifest, no service worker, no browser storage and no online detection. `index.html` still carries Replit boilerplate and loads Google Fonts from a CDN.
- `vite.config.ts` does support `BASE_PATH`, and wouter honours it, which helps mount the POS under a launcher.
- The inactivity "lock" is actually a full server sign-out.
- Face-scan placeholders are still in the code, against the brief's no-biometrics rule.
- The UI collapses the permission list into a single manager/staff flag.
- The till flow exists twice: `Till.tsx` (1,966 lines) and `MobileTill.tsx` (1,530 lines).

I did not run the app. These findings come from reading the source, grep counts and the brief.

## api-structure
The Sprint 1 API is a small Fastify 5 app, about 2,900 source lines, built by a single DI-friendly `buildApp({env, db, fileStorage})`. It registers two global plugins (session, idempotency) and 12 flat route plugins, all validated by zod with OpenAPI at /docs/json. The route files are already Fastify plugins, so registering HR, scheduling, analytics, messaging and booth modules is mechanically easy.

Three foundations the brief depends on are missing.

1. **No service layer.** CLAUDE.md §8 requires "logic in services, every write in a transaction". In practice most business logic is Drizzle/Postgres code inside route handlers. There are no `db.transaction` calls anywhere, and every ID is minted on the server.
2. **Most money-path logic is not portable.**
   - `packages/shared` is pure and would run on a Raspberry Pi or in a browser. It covers only ticket kid/adult line pricing, rate mode, money, phone, dates, ids and zod shapes.
   - Sale totals, tax computation, discounts, F&B, drop-off and vouchers live only in `apps/pos/src/lib`. That code works in whole baht and reads module-global catalog getters.
   - `services/tax.ts` is coupled to the database.
3. **Several pieces the brief needs do not exist:**
   - module registry, module enablement and feature flags;
   - device/box identity, signed offline tokens, a sync protocol and a WebSocket channel;
   - a job runner, and CORS or a cross-app cookie strategy;
   - generated API client and shared UI packages;
   - an API build artifact and a box-agent app.

Tests are solid: 50 `app.inject` integration tests on real Postgres plus 16 unit tests. The `buildApp` DI style extends naturally to a `buildAgent({devices})` with in-process simulators and a cloud+box convergence harness. Playwright is not run in CI, and the file-storage tests skip in CI.

The repo is a nested workspace inside the Replit-export git root. `apps/pos` is one SPA holding till, admin, /book, customer display and mobile shell, so hosting a launcher, multiple frontends and imported apps needs a layout restructure first.
