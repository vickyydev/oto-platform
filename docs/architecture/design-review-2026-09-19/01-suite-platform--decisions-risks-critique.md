# DESIGN suite-platform

## Summary
Build the suite as ONE origin, ONE Fastify modular monolith, ONE Postgres (schema-per-module on a shared core) and MANY small Vite frontends mounted by path (`/` launcher, `/pos/`, `/admin/`, `/team/`, `/analytics/`, `/satang/`, `/inbox/`), all built from one monorepo on a shared UI kit and app-shell package. With one origin, the existing host-only `oto_session` cookie (apps/api/src/plugins/session.ts:10,44) already IS single sign-on; no OIDC server, no parent-domain cookie, no CORS for staff apps. The launcher is just the app at `/` rendering `GET /api/me/apps`, which is computed from a code-defined registry of apps and modules, per-operator/branch module entitlement, and the account's effective permissions. The client's 'turn pages and features on and off per role/account' request is met with ONE mechanism, not a second flag system: pages and features are permission strings (`<module>:page:<x>`, `<module>:feature:<x>`) declared in each module's manifest, synced to the DB on every deploy, granted through operator-scoped custom roles, and overridable per account with allow/deny. Two distinctions carry the design: (1) an APP (deployable frontend + launcher tile) is not a MODULE (domain + permission namespace + pg schema + API prefix) - the OTO App tile hosts six or seven modules; (2) the strangler pattern applies to CODE (keep the approved UI, replace backend/auth/db with platform modules), not to live production traffic - I do not recommend running two systems of record for employee/branch data. Public Website and Booking are separate deployables on separate hostnames that never see the staff cookie and only reach `/public/*`. Device surfaces (kiosk, booth, customer display, timekeeping kiosk) are not launcher apps; they use one device-activation mechanism. Before any of this, three live defects must be fixed because centralising amplifies them: the role-assignment privilege escalation (apps/api/src/routes/accounts.ts), the `ALL` permission bundles for admins (packages/shared/src/permissions.ts), and ad hoc tenant scoping. The biggest unknown is not technical: whether each Replit app is a mock-data prototype like oto-till (replit.md: 'Front end only - no backend, database, or auth') or a live system with data. That single fact per app changes its cost by an order of magnitude, so the intake assessment is a hard gate before any estimate.

## Key decisions
- **One origin for all staff apps, path-mounted (`/`, `/pos/`, `/admin/`, `/team/`, `/analytics/`, `/satang/`, `/inbox/`) behind the same `/api`; the existing host-only session cookie is the SSO mechanism.** — The session plugin (apps/api/src/plugins/session.ts) already issues a host-only, Path=/ cookie and the POS already supports `BASE_PATH` with wouter (apps/pos/vite.config.ts, apps/pos/src/App.tsx). SSO therefore costs nothing, needs no CORS or token exchange for staff apps, and keeps instant revocation. Path mounting also keeps a later move of any frontend to a static host a routing change only. (rejected: Subdomain per app with `Domain=.otoplay.co` cookie: rejected - the cookie would be sent to every box hostname under `*.central.otoplay.co` and exposed to website XSS. Central OIDC/auth server with code exchange per app: 10+ days of work and a new failure point for zero user-visible benefit at this scale. JWT in localStorage shared across apps: loses instant revocation and is readable by any XSS.)
- **Modular monolith: one Fastify process, one pool, modules as encapsulated plugins under `/api/<module>`, boundaries enforced by lint rules and a `public.ts` interface per module; cross-module effects via an in-process Postgres-backed queue.** — Matches brief section 9 (one pool, 1 CPU tier), preserves single-transaction integrity across HR/access/POS, and the existing DI-style `buildApp` plus embedded-Postgres test harness extends to it directly. Without enforced boundaries eight imported apps would produce a big-ball schema and handler-level Drizzle everywhere. (rejected: Service per imported app (keeping each Replit backend alive): multiplies auth, DB connections, deploys and tenant-scoping bugs; contradicts 'central database'. Backend-for-frontend per app: unnecessary indirection for first-party SPAs.)
- **Separate APP (launcher tile, deployable frontend) from MODULE (domain, permission namespace, pg schema, API prefix) in a code-defined registry (`packages/registry`) consumed by both API and frontends.** — The OTO App is one tile but at least six domains (time, tasks, events, sop, hr, sched); the POS tile spans pos, catalog, fnb, care, wallet, stock. Permissions and entitlements must be per module; tiles must be per app. One module key used as namespace + schema + prefix + folder makes ownership unambiguous. (rejected: One module per app: forces all-or-nothing enablement of the whole OTO App and blocks reuse (e.g. `care` used by both POS and Team). Registry stored only in the DB: permissions must be compile-time checkable and versioned with the code that enforces them; the DB holds a synced mirror.)
- **Pages and feature switches are permission strings (`module:page:x`, `module:feature:x`) evaluated by one engine: entitlement (operator/branch module + feature on/off) AND (role grant OR account allow) AND NOT account deny. Deny exists only at account level.** — Directly answers the client's SCRUM-21/22 feedback ('more options to turn on and off specific pages or functionality') with one source of truth for API guard, nav rendering, launcher and box snapshot. Keeping roles a pure union preserves the tested Sprint 1 resolver and keeps 'why can this person do X' explainable. (rejected: A separate feature-flag system beside permissions: two sources of truth that will disagree, and the API would not enforce the flags. Role-level deny or role ranking/hierarchy: makes effective-access reasoning order-dependent and hard to explain in the admin UI.)
- **Idempotent registry sync on every deploy (modules, permission catalog, system-role bundles); operator-scoped custom roles with unique `(operator_id, key)`; system roles code-owned, custom roles data-owned with new permissions defaulting off.** — Today the seed is a no-op once operator 'OTO' exists (packages/db/src/seed/index.ts) and `role_name_unique` is global on name (packages/db/src/schema/tenancy.ts:122), so new module permissions would never reach an existing database and custom roles are impossible. (rejected: Sync at process boot: races on multi-instance and hides failures; a release step fails the deploy loudly. Hand-written migrations for each permission change: slow and error-prone across eight modules.)
- **Delegation rule for all grants: target account in the granter's operator, granted scope within the granter's coverage, granted permission set a subset of the granter's effective set at that scope; `platform_admin` only by platform admins. Remove the `ALL` bundles; `sensitive` permissions are never wildcard-granted and their reads are audited.** — A branch manager can grant themselves platform_admin today (apps/api/src/routes/accounts.ts). Once one permission service guards HR contracts, payroll and finance, that defect and `operator_admin: ALL` (packages/shared/src/permissions.ts) become the most damaging issues in the system. (rejected: Numeric role ranks: brittle with custom roles and scopes. Leaving `ALL` for operator_admin and trusting process: IT admin and HR/finance access must be separable.)
- **Sign-in is a shared component (`<SignInGate>` in `packages/app-shell`) rendered in place by every app, not a redirect to a central login page; the launcher is simply the app at `/`. The POS lock becomes a local lock that keeps the session, with `POST /auth/unlock`.** — An installed iOS PWA scoped to `/pos/` opens out-of-scope navigations in an overlay browser, and the launcher is not in the POS service-worker cache when offline. Today the POS inactivity lock deletes the server session every 2 minutes (apps/pos/src/auth/OperatorContext.tsx), which also contradicts brief section 5. (rejected: Central `/sign-in?next=` redirect for all apps: breaks installed PWAs and offline unlock.)
- **Un-ported apps appear in the launcher as `external` tiles that open the existing deployment with its own login; no SSO bridge into legacy backends.** — Delivers the professional launcher immediately and keeps effort on the replacement modules. Bridging auth into backends that will be discarded is wasted work and creates a second trust path. (rejected: Reverse-proxying legacy apps under the suite origin with an injected identity header: puts un-audited Replit code on the staff origin where any XSS reaches every app, and requires modifying each legacy auth layer.)
- **Strangle code, not production traffic: imported apps keep their UI while backend/auth/db are replaced by platform modules; the live OTO App is cut over in one rehearsed window, not module by module across two live databases.** — Employee, branch and department data are referenced by nearly everything (SCRUM-158 note). Two systems of record with sync between AWS RDS and the platform is the highest-risk design available; brief section 12 already assumes the old system stays live until cutover. (rejected: Incremental live strangling with dual writes or CDC between the legacy RDS and the platform: justified only if the client cannot tolerate a single cutover, and then only for leaf domains with no shared master data.)
- **Public Website and Booking are separate deployables on their own hostnames, static builds, reaching only `/public/*` on `api.otoplay.co`; OTO App guest links (RSVP, menu selection, camp registration, drop-off forms, guest check-in) consolidate into the booking app as tokenised links.** — Different audience, cache and SEO profile, and a different threat model; they must never share an origin or cookie with staff apps. SCRUM-122 already flags three overlapping public intake forms. (rejected: Keeping `/book` inside the POS SPA (current state): ships the whole staff bundle to the public and puts public traffic on the staff origin. Next.js with SSR for booking: a second server runtime on a 1 CPU plan for a flow that does not need SEO.)
- **Postgres schema per module on a shared `core`, one migration stream, FKs only into core; legacy dumps land in local `legacy_<app>` staging schemas with a `core.legacy_map` provenance table.** — Generic names already taken in `public` (employee, department, role, account, session, item, transaction, booking) will collide with every import. With only a seeded dev database today, the move is `ALTER TABLE ... SET SCHEMA`; after Sprint 2 and the migration it is a data project. (rejected: Table-name prefixes in `public`: works but gives no grant boundary and poor ownership visibility. Database per app: breaks the central-database requirement, single transactions and the one-pool rule. Schema per tenant: already rejected in ARCHITECTURE.md.)
- **Make `oto-platform` its own repository root and quarantine raw Replit exports in `imports/` outside the workspace globs.** — The workspace is nested inside the Replit export whose root `pnpm-workspace.yaml` strips every non-linux-x64 native binary and excludes `@replit/*` from release-age checks; CI lives at the parent; `apps/pos/vite.config.ts` reaches three directories up for assets. Seven more exports dropped into that root would entangle un-audited code with the platform build. (rejected: Adding each Replit app under the parent root's `artifacts/*`: inherits Replit's overrides and mixes lockfiles and unreviewed dependencies into CI.)

## Risks
- [critical] Unknown nature of the seven imports. oto-till is explicitly a front-end-only prototype on mock data (replit.md). If Satang, Analytics, Radar, Inbox and Wheel are the same, 'merge' means building their backends from scratch; if any is a live system with data, it means migration plus parallel run. Stacks are also unknown (the root `.replit` lists python-3.11; the catalog hints at Expo). Scope cannot be sized today. — MITIGATION: Make the intake assessment (section 9, step 1) a hard gate: 1-2 days per app, written, classifying A/B/C/D before any estimate or commitment. Ask the owner now which apps hold real data and who uses them daily. Time-box the platform kernel work so it is ready before the imports arrive.
- [critical] Access-control defects amplified by centralisation: any holder of `admin:role:assign` can grant `platform_admin` to anyone (apps/api/src/routes/accounts.ts); `operator_admin` and `platform_admin` get `ALL` (packages/shared/src/permissions.ts); `GET /accounts/:id/permissions` and `GET /members/:id` skip operator checks. With HR contracts, payroll and finance behind the same engine these become data-breach paths. — MITIGATION: Fix before any new module is mounted: delegation rule, target-operator checks, removal of ALL bundles, `sensitive` permission flag with audited reads, mandatory-operator repo layer. Add negative tests (branch manager cannot escalate; cross-operator id returns 404).
- [high] Identity reconciliation across apps and the production dump. Platform accounts are phone-keyed per operator; legacy users may be keyed by email, username or Replit identity; `findAccountByPhone` ignores operator; legacy password hashes will not verify under argon2; password reset requires `phoneVerifiedAt`. The same human may exist as employee, account, and customer member. — MITIGATION: Add `account.email` and `core.account_identity(provider, subject)`; profile the dump for phone coverage and duplicates first; migrate staff as `invited` and reuse the SMS setup flow (or verify-then-rehash if the legacy hash is a standard format); keep employee, account and member as separate linked tables rather than one 'person' table; resolve sign-in by phone plus operator.
- [high] Same-site exposure. `www.otoplay.co`, `app.otoplay.co` and every Pi at `*.central.otoplay.co` are the same site, so SameSite=Lax does not stop a compromised box or a website XSS from sending credentialed state-changing requests to the suite, or from tossing cookies onto the parent domain. — MITIGATION: `__Host-` prefixed host-only cookie, Origin/Sec-Fetch-Site check on every mutating request, no parent-domain cookies ever, strict CSP. Defence in depth: move box LAN names to a separate cheap registrable domain before any hardware is deployed.
- [high] Two systems of record during transition. The OTO App is live on AWS with real HR/timekeeping data while the platform grows its own `employee`/`branch`/`department`. Any period where both accept writes to the same master data produces divergence that is expensive to reconcile. — MITIGATION: No dual writes. Platform `core.employee` is populated only by repeatable migration rehearsals until cutover; external tiles link out to the legacy app meanwhile; one rehearsed cutover window with legacy set read-only; rollback plan written first.
- [high] Overlapping concepts across apps: supervised drop-off/nanny/camp check-ins (SCRUM-123 vs SCRUM-75..79), events/parties (X3 vs POS Parties vs P4), three public intake forms (SCRUM-122), activity logbook vs audit (SCRUM-168), staff vs promo vs booth vouchers, Radar vs Analytics, org structure (SCRUM-158) vs Sprint 1 tenancy. Porting both sides of an overlap doubles cost and creates conflicting truths. — MITIGATION: A one-page concept-ownership table agreed with the client before porting: each concept has one owning module; the losing implementation's UI is either dropped or re-pointed at the owner's service.
- [high] Permission model usability. Several hundred permission/page/feature strings across ~18 modules will overwhelm a non-technical park administrator; misconfiguration is as dangerous as a bug. — MITIGATION: Role templates per job (reception, nanny, kitchen, HR officer, accountant); matrix grouped Module -> Page -> Actions with dependency auto-hints from manifest `requires`; account overrides limited to tri-state; 'effective access' explainer and 'view as' preview; change log of access edits surfaced from audit.
- [high] Secrets and Replit-specific dependencies inside exports: keys in `.replit`/env files or source, Replit Auth, `@replit/object-storage`, Replit DB, `lib/integrations/*` AI helpers, `stripe-replit-sync` (whitelisted in the root pnpm-workspace.yaml). — MITIGATION: Secret scan before first commit and rotation of anything found; every Replit service mapped to a platform equivalent at intake (platform session, files service on S3/MinIO, `ai` module, payments via 2C2P); `imports/` never built or deployed.
- [medium] Single origin means one XSS or one malicious dependency in any mounted app can act as the user across all apps, and apps share localStorage/IndexedDB and the service-worker namespace. — MITIGATION: First-party code only on the staff origin; strict per-app CSP, no third-party CDNs (self-host fonts); dependency audit at intake; launcher registers no service worker, POS registers at `/pos/` only, CI check that nothing registers at `/`; storage keys namespaced `oto:<app>:`.
- [medium] Capacity and deploy coupling on one 1 CPU Render service now carrying eight apps' API traffic, static assets, the box WebSocket hub, webhooks and jobs; per-request session + permission DB lookups multiply with app count; every deploy restarts everything. — MITIGATION: CDN in front with immutable hashed assets; small in-process session/permission cache (30-60 s, invalidated on revoke - coherent because single instance) keyed by `perm_version`; launcher badges cached 60 s and time-boxed; nightly rollups for analytics; boxes reconnect with backoff. Escape hatches that need no redesign: move frontends to a static host by route; split a worker process with a small capped pool.
- [medium] Stack mismatches: a Next.js app using server components/actions, a Python analytics app, an Expo wheel app. Each can turn 'keep the UI' into a partial rewrite. — MITIGATION: Decision table in section 9: Next -> Vite SPA or static export with basePath; Python -> SQL rollups + TS endpoints unless genuine ML (then a read-only sidecar); Expo wheel -> rebuilt as web `apps/booth` reusing art. Budget a porting spike per non-template app before committing.
- [medium] 'Keep the approved UI' versus 'one professional suite': seven apps built independently will differ in theme, spacing, navigation and tone; a full visual unification is a large, low-value project. — MITIGATION: Unify chrome and tokens only (AppFrame, app switcher, sign-in, toasts, states, fonts, colours); leave inner screens as approved; replace private shadcn copies with `@oto/ui` opportunistically.
- [medium] Repo restructure and route renaming collide with the start of Sprint 2 feature work. — MITIGATION: Do it first, in a short freeze, as behaviour-preserving refactors covered by the existing 50 integration tests; add Playwright (chromium) to CI before moving POS files.
- [medium] AI features across modules (Ask OTO with citations SCRUM-150, customer enquiry AI SCRUM-107, AI settings SCRUM-180) send staff SOPs and customer conversations to an LLM provider; PDPA and key-management implications, plus legacy face-identity data (SCRUM-118) that the brief forbids. — MITIGATION: One `ai` module owns provider keys, per-operator settings, prompt/response logging policy and redaction; modules call it through `public.ts`. Face data is excluded from migration and deleted at cutover with a recorded decision; timekeeping kiosk uses PIN or QR badge.
- [medium] Phone-only sign-in for back-office and external users (accountant in Satang, advisors and casual workers SCRUM-160, owners travelling with foreign SIMs); SMS deliverability and cost; in-memory throttle keyed on proxy IP with `trustProxy` unset would lock all sign-ins once the launcher is the single door. — MITIGATION: Keep phone as primary identifier; add optional verified email as recovery channel and TOTP step-up for roles holding `sensitive` permissions; set `trustProxy`, move throttle buckets to Postgres keyed by phone and device.
- [low] Launcher literalism: the owner said the start page 'shows all OTO apps'; the brief says 'pick an app you have access to'. Showing locked tiles to floor staff leaks the existence of HR/finance tools and clutters a reception iPad. — MITIGATION: Permitted apps only for staff; owners/operator admins additionally see 'Not enabled' and external tiles; single-app accounts bypass the grid. Confirm with the owner.

## Changes to Sprint 1 foundations
- Extract `oto-platform` into its own git repository root with history; move CI to it; remove the `@assets` alias that reaches into the Replit export (apps/pos/vite.config.ts); add an `imports/` quarantine folder outside the workspace globs.
- Fix the role-assignment privilege escalation and missing operator checks in apps/api/src/routes/accounts.ts (POST /accounts, POST /accounts/:id/role-assignments, GET /accounts/:id/permissions) with the delegation rule; add negative tests.
- Remove `ALL` bundles from packages/shared/src/permissions.ts; split the single PERMISSIONS array into per-module manifests in a new `packages/registry`; add `module:page:*` and `module:feature:*` kinds and a `sensitive` flag.
- Move `grantCovers`, `hasPermission`, `resolveEffectivePermissions` types and the new entitlement/override evaluation from apps/api/src/services/permissions.ts into `packages/authz` so API, frontends and box-agent share one evaluator.
- Schema: replace `role_name_unique` on name (packages/db/src/schema/tenancy.ts:122) with unique `(operator_id, key)` plus a partial unique for system roles; add `is_system`; add `core.module`, `core.permission`, `core.operator_module`, `core.account_permission_override`, `core.account_app_pref`, `account.perm_version`, `account.email`, `core.account_identity`; give `role_assignment` `granted_by` and `revoked_at` instead of hard delete; timestamps on `role_permission`.
- Replace seed-once role bundles (packages/db/src/seed/index.ts) with an idempotent `platform:sync` release step that upserts modules, permission catalog and system-role bundles on every deploy.
- Move all 37 tables out of `public` into per-module pg schemas (`core`, `pos`, `catalog`, ...) via Drizzle `pgSchema` while only a seeded dev database exists; add `core.legacy_map`.
- Restructure apps/api/src/routes/* into `apps/api/src/modules/<key>/{routes,service,repo,public}.ts`; introduce `withTx` so audit rows commit atomically with the change (currently zero `.transaction(` calls despite the comment in apps/api/src/services/audit.ts); make `operatorId` a mandatory repo argument; fix the unscoped lookups in apps/api/src/routes/members.ts (GET /members/:id) and apps/api/src/routes/public.ts:106-110.
- Extract `packages/api-kit` (the `App` type currently in apps/api/src/app.ts, `AppError`, auth decorators, audit, `defineModule`) so module code does not import from the app entrypoint.
- Namespace API routes as `/api/<module>/...` and add a per-module enabled guard; regenerate the POS client from `/docs/json` into `packages/api-client` instead of the hand-written types in apps/pos/src/api/platform.ts.
- Session/cookie hardening in apps/api/src/plugins/session.ts and apps/api/src/app.ts: `__Host-oto_session`, `COOKIE_SECURE=true` in production, `trustProxy`, Origin/Sec-Fetch-Site check plugin for mutating requests, host guard separating `app.` staff routes from `api.` public/hook/box routes, Postgres-backed sign-in throttle keyed by phone and device, operator-aware `findAccountByPhone`.
- Add `GET /api/me/apps` (and cached badges) and extend `GET /api/me/permissions` to return grants, scopes, entitlements and `permVersion`; add `POST /api/auth/unlock`.
- POS: replace the `isManager` boolean and `managerOnly` gating (apps/pos/src/auth/OperatorContext.tsx, apps/pos/src/components/admin/AdminAccessGate.tsx, adminSections.tsx) with `can()` from `packages/app-shell`; make the inactivity lock local instead of calling `signOut`; remove face-scan placeholders (apps/pos/src/components/auth/LockScreen.tsx, `mockFaceScan`); gate `/station-setup` by permission.
- Split the POS SPA: `/book` -> `apps/booking`; platform administration screens (access, branches, operators, devices, audit) -> `apps/admin`; module configuration (tickets, tax, menu, discounts...) stays with the POS app under page permissions; lift `apps/pos/src/components/ui/*` (55 components) and theme tokens into `packages/ui`; self-host fonts and strip Replit boilerplate from apps/pos/index.html.
- Make `POST /public/bookings` idempotent by client-minted booking id and let the idempotency plugin accept non-account principals (apps/api/src/plugins/idempotency.ts); stop caching 5xx responses.
- CI: add Playwright on chromium, a MinIO service so file tests stop self-skipping, ESLint coverage for apps (currently `apps/pos/**` is ignored in eslint.config.mjs), a module-boundary lint rule, and an API build step so a deployable artifact exists.

## Disagreements with brief
- Brief section 2 (Decided): 'Sprint 2 is one continuous run that finishes all remaining software.' With the addendum adding seven apps of unknown stack and state plus 58 X-stories, a single undifferentiated run is unsafe. Better: three gated milestones - (1) platform kernel (repo split, services+transactions, access fixes, registry, launcher, app-shell/UI kit), (2) POS + box money path, (3) imported apps in intake order - with the intake assessment as a formal gate before any imported app is estimated. This is a planning change, not a request for module-by-module client sprints.
- ARCHITECTURE.md section 2 (Decided): 'Admin / booking frontends ... likely Next.js.' Reject. Staff apps gain nothing from SSR, and a Next server is a second runtime and a second potential DB client on a 1 CPU plan. Use Vite SPAs for all staff apps and for Booking (it already exists as React+Vite inside the POS); use a static/SSG build for the Website.
- Brief section 6 (Decided): box hostnames under the public zone `central.otoplay.co`. Safe only if session cookies stay host-only and mutating requests are Origin-checked, because boxes, website and staff suite are then the same site and SameSite gives no protection between them; a physically compromised Pi holds a valid certificate for a sibling hostname. Better: a separate inexpensive registrable domain for box LAN names (DNS-01 works identically). Cheap now, awkward after hardware is deployed. If the owner keeps the current zone, the `__Host-` cookie and Origin check become mandatory, not optional.
- Brief section 11 (Decided): the booth is 'managed from the POS admin like any other' station. Stations, boxes and device sessions also serve the OTO App's reception and timekeeping kiosks (SCRUM-116/117: 'Build one mechanism, not two'), so device management belongs in the central Admin app under a `devices` module, with booth game configuration contributed by the `booth` module. This is also what the client's own Sprint 1 feedback ('this will become centralised') points to.
- Brief section 9 (Decided): 'One connection pool in the API ... workers and analytics do not open their own.' Correct as a starting rule, but it is a proxy for 'do not exhaust connections on a small Postgres', not a goal. With eight apps, a WebSocket hub, webhooks and jobs in one 1 CPU process, plan the escape hatch now: a second worker process with a hard-capped pool of 2-3 connections is acceptable when job load starts to hurt request latency. Do not contort the design to avoid it.
- Sprint 1 foundation (Decided in CLAUDE.md/permissions.ts): `platform_admin` and `operator_admin` receive ALL permissions. Unsafe once HR, payroll and finance modules exist. Replace with explicit per-module bundles and a `sensitive` flag that wildcard grants never include.
- Sprint 1 foundation (Decided): phone + password as the only credential. Keep phone as the primary identifier, but it is insufficient alone for a suite that includes finance and HR and external/casual users: add optional verified email for recovery and TOTP step-up for accounts holding sensitive permissions, plus PIN/QR-badge credentials for device surfaces (no biometrics, per brief section 13 - which means SCRUM-118 face enrolment must be dropped, not migrated).

## Open questions
- For each of the eight Replit apps: is it a UI prototype on mock data (like Oto POS) or a live system with real users and data? Which are used daily, and by whom? The production Postgres dump - is it only the OTO App's database, or do Satang, Analytics, Inbox or the Wheel have their own data too?
- What stack is each app (React/Vite + Express template, Next.js, Python, Expo/React Native)? In particular, is 'Wheel Fortune Mobile' a phone app or a web page, and what differs between its two variants?
- 'Asset Manager' shows a 'Customer Inbox - Roles, Routing & Workflow' thumbnail. Is it the customer messaging inbox (brief section 14.6), a genuine asset register (SCRUM-167), or both?
- Oto Radar vs Omni Analytics: two separate products for different audiences, or can Radar become the Overview page of Analytics?
- Satang: what does it do today (expense approvals, petty cash, accounting checklists, payroll), who uses it, and does it overlap the POS cash management and settlement export in brief section 10?
- Launcher: should floor staff see only the apps they may open (recommended), with owners/admins also seeing not-yet-enabled apps? Should an account with a single app (reception) skip the grid and open the POS directly?
- Domain names: which hostname for the staff suite (e.g. app.otoplay.co), booking and website? Who controls DNS and which provider (needed for box DNS-01 too)? Is a separate inexpensive domain for the Pi box hostnames acceptable?
- Who may see HR contracts, pay data and finance records? Is it acceptable that an IT/operator admin does NOT automatically get them, and that such access requires an explicit grant plus a second factor?
- Sign-in: is phone + password acceptable for every user including the accountant, external advisors, casual workers and people with foreign numbers? May we add email as a recovery channel and an authenticator-app step for finance/HR roles?
- Migrated staff accounts: is a one-time SMS setup for every employee at cutover acceptable (cost and friction), or must existing passwords keep working?
- The existing OTO App uses face identity for the timekeeping kiosk (SCRUM-118); the brief forbids biometrics. Confirm it is replaced by PIN or QR badge, and that stored face data is deleted rather than migrated.
- Overlaps needing a single winner: drop-off/nanny/camp check-in (OTO App vs POS supervision), events and parties (OTO App Events vs POS Parties), the three public intake forms, staff vouchers vs promotional vouchers vs booth vouchers, activity logbook vs the platform audit log. Which implementation does the client consider the approved one in each case?
- Organisation model (SCRUM-158): beyond operator -> branch -> department, do 'locations' and a reporting hierarchy need to drive permissions (e.g. a department head sees only their department across branches)?
- Multi-tenancy: will the suite ever serve a second company (another operator), or is 'operator' effectively always OTO? This decides how much tenant-isolation hardening (e.g. row-level security) is worth buying now.
- Cutover appetite: is one planned cutover weekend for the OTO App acceptable, or does the business require moving module by module while the old app stays in use?
- Is a CDN/WAF in front of Render (e.g. Cloudflare) acceptable, and is there an existing account?
- Website: who edits the content today and how (code in Replit, or do they expect a CMS)? Does it have forms or data that must be kept?

## Sequencing
- Week 0, before anything else: ask the owner the real-vs-prototype question for every app and request all exports plus the dump together, so intake assessments can run in parallel with kernel work.
- Step 1 - Safety fixes on Sprint 1 (2-3 days): role-assignment delegation rule, operator checks on id routes, unscoped public lookup, cookie/trustProxy/Origin hardening. These are live defects independent of every other decision.
- Step 2 - Repo and structure freeze (about 1 week, behaviour-preserving, tests green throughout): extract the repo root; add Playwright and MinIO to CI; restructure API into modules with `withTx` and the repo layer; extract `api-kit`, `authz`; move tables into pg schemas. Do this before Sprint 2 adds tables - the cost rises sharply afterwards.
- Step 3 - Platform kernel (about 2 weeks): `packages/registry` with manifests for core/pos/catalog; registry sync; new access tables, evaluator with entitlements and account overrides; `/me/apps`, `/me/permissions`; `packages/ui` and `packages/app-shell` lifted from the POS; `apps/launcher` with external tiles for every un-ported app; role matrix and account override screens in `apps/admin`. This is the client-visible answer to the Sprint 1 review feedback and should be demoed early.
- Step 4 - POS re-seated on the kernel: mount at `/pos/`, `can()` instead of manager/staff, local lock, in-place sign-in, `/book` split into `apps/booking`. Then the box/money-path work proceeds on a stable base (the launcher and registry have no dependency on the box, so both tracks can run in parallel after Step 3).
- Step 5 - Intake assessments as exports arrive (1-2 days each), producing the concept-ownership table and a per-app class and estimate. No porting before the table is agreed with the client.
- Step 6 - Port order: class A prototypes with no legacy data first (Inbox/messaging, Wheel/booth, Radar+Analytics on rollups, Satang) because they carry no migration risk and flip tiles to native quickly; the live OTO App last, module-complete on staging (suggested internal order: core org/people -> time -> sched -> tasks -> sop -> events -> perks), with migration rehearsals running from the day the dump arrives.
- Step 7 - Website can move at any time: it has no dependency on the platform beyond `/public/*` reads and should not be on the critical path.
- Keep a standing rule throughout: nothing from `imports/` is mounted on the staff origin until it meets the intake definition of done (no own auth, no own DB connection, manifest permissions, audited writes, repo-layer tenancy, in CI).

# CRITIQUE — verdict: sound-with-changes. The overall shape is right for a two-branch business on a 1 CPU Render tier: one origin, a host-only cookie, a modular monolith, the app/module split, registry sync, and an intake gate. I checked the repo claims and they hold: 0 `.transaction(` calls, 37 tables in `public`, a seed that does nothing on re-run, `role_name_unique` on name alone, an inactivity lock that calls `signOut`, the unscoped `/public/member-tier` lookup, no deploy config, no service worker or manifest, and a nested workspace with CI at the parent.

Four areas are under-designed and will cause failures in use:

1. **Privilege escalation is wider than stated.** The delegation rule covers role grants but not credential resets, phone changes or role editing. A branch manager can take over the platform admin account today through `temp-password`.
2. **The session and lock model breaks on one origin.** A local POS lock that keeps a suite-wide cookie leaves HR, Admin and Finance open on a shared iPad. The session row also carries a mutable branch and station that every app and tab would share.
3. **The permission model cannot express the imported app's main access patterns.** There is no self or "my reports" scope, and the evaluator cannot filter lists. Page and feature toggles are not enforced by the API. Nobody inside the client can grant sensitive permissions once the ALL bundles are removed.
4. **The migration and interim story has gaps.** "No two systems of record" contradicts the proposal's own sequencing. The migration covers Postgres only, not files, signed contracts, secrets, webhooks or public links already in circulation. "Contract skew is impossible" is false for the POS PWA and the boxes.

Estimates of 1 week plus 2 weeks for the kernel are not credible against the actual state of the repo. The plan also front-loads about a month of platform work before a till can sell a ticket. Fix findings 1-9 in the design before money is spent. Trim the kernel to a minimum and re-cut the sequence.
