# SCRUM-193: Attention Engine boundary and job ownership audit

## Read-only audit, 1 October 2026

**Status: BROKEN for multi-tenant use.** This was a source and read-only staging audit, not a mutation test. No refresh, resolve, rule-setting change, account creation, or synthetic Attention item was performed. On live oto-app-staging, the existing launcher-signed administrator received 200 from `/api/attention-items?limit=1`, `/api/attention-items/counts`, `/api/attention-items/last-run`, `/api/attention-rules/config`, an own-branch counts request, and the first returned item's `/check-condition`. The unfiltered count was 46 open items, and the list returned an item. These checks establish that the current screen endpoints answer for the administrator. They do not establish tenant or restricted-branch isolation; no second-tenant identity was used for this audit.

`attention_items` has `branch_id`, `employee_id` and `contract_instance_id`, but **no `tenant_id`** (`shared/schema.ts:1339`; baseline migration `migrations/0000_otoapp_baseline.sql:177`). Branch is nullable, so branch-only filtering cannot classify company-wide or orphaned items. `GET /api/attention-items` accepts any supplied branch ID or no filter, and `storage.getAttentionItems` then queries the shared table without a signed-in tenant or allowed-branch predicate (`routes.ts:6755`, `storage.ts:3607`). `GET /api/attention-items/counts` has the same issue (`routes.ts:6785`, `storage.ts:3647`). Any authenticated user can call these endpoints even though the client page is manager/admin only. An explicit foreign branch ID is not refused by either route.

`POST /api/attention-items/:id/resolve` requires manager role but `storage.resolveAttentionItem` updates by item ID alone; it never checks tenant or branch and can resolve another branch's or tenant's item (`routes.ts:6797`, `storage.ts:3688`). `GET /api/attention-items/:id/check-condition` reads any item ID and evaluates its employee without ownership checks (`routes.ts:6844`, `storage.ts:3850`). Admin-only `GET /api/attention-items/diagnostics/:employeeId` calls a global employee lookup and can evaluate another tenant's employee if the ID is known (`routes.ts:6833`, `attention-engine.ts:1378`). The per-process `lastCalculatedAt` returned by list/last-run is not a durable run record or tenant-specific result.

`POST /api/attention-items/refresh` is available to every authenticated user and invokes global reconciliation (`routes.ts:6812`). The engine loads all employees and contracts and scans up to 10,000 open Attention items across tenants when resolving stale rules (`attention-engine.ts:1049-1155`). Scheduling evaluation iterates all branches and likewise scans global open scheduling items (`attention-engine.ts:1185-1351`). Storage upsert, auto-resolve and lookup use rule/entity keys without tenant scope (`storage.ts:3731-3855`). The shared `attention_rules_config` lives in `settings`, whose key is globally unique and has no tenant column; an administrator in any tenant can read or overwrite the same rule configuration (`routes.ts:6868`, `shared/schema.ts:1183`). The generic Data Admin registers Attention Item as an editable model; it is mounted behind global-admin access, so it also needs explicit consideration at cutover.

**Job ownership is not built to the S2-17b contract.** `server/index.ts:140-161` starts full reconciliation five seconds after each web-process boot and every six hours through `setInterval`. `startScheduledJobs()` runs other timers, including a no-show check immediately and every ten minutes (`scheduled-jobs.ts:427-450`); those jobs create or resolve Attention items. There is no advisory lock, platform runner registration, or `ops_run` write in these paths. Multiple web instances or overlapping deployments can run the same reconciliation concurrently. The read-only staging call confirmed a last-run timestamp, but not durable ownership, completion, or failure evidence. The automatic six-hour job calls only `runFullReconciliation`; scheduling alerts are included by the manual `runAttentionEngine` path, so their automatic refresh is not established. S2-17b requires the jobs to run under platform advisory locks with `ops_run`, or in-app with the same contract through the directory API (`docs/progress/SPRINT_2_PLAN.md:2513-2516`).

**Needs from the platform lane:** an additive `otoapp.attention_items.tenant_id` migration with backfill from the owning employee, contract, or branch and an explicit disposition for branchless/ambiguous legacy rows; tenant-consistent foreign keys or validation, tenant-scoped indexes and deduplication for rule/entity keys; tenant-scoped Attention rule settings or an approved platform-wide configuration contract; and a job-owner/`ops_run` interface with advisory locking for reconciliation, scheduling alerts and Attention-producing scheduled checks. The app lane can then fail closed on missing/ambiguous tenant rows, restrict list/count/item/diagnostics/resolve to the signed-in tenant and permitted branches, and limit refresh to an authorized tenant-scoped run. Until the schema/cutover and job contract exist, the module cannot be marked deployed for multi-tenant acceptance.
