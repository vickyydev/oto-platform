# SCRUM-193: leave and holidays staging acceptance

On 1 October 2026, a launcher-signed administrator used one clearly labelled synthetic employee on the staging OTO App. The 820 × 1180 screenshots were captured from the live browser and visually reviewed.

An annual leave record for 3 October was created through `/api/time-off` (201) and read from the employee time-off route (200, one matching record). A second request for the same employee and date was refused with 409. The My Shifts day view rendered the **Annual Leave** card and synthetic note in `scrum-193-staging-my-leave.png`. A labelled 6 October public holiday was created (201), appeared in the 2026 holiday read (200), and is visible in `scrum-193-staging-public-holiday.png`. Anonymous time-off and public-holiday reads each returned 401.

The holiday, leave record and employee were removed with 204. Final searches found zero matching synthetic employees, public holidays or employee time-off records. The screenshot is evidence of the transient staging state, not a record left active.

One date bug was reproduced before the successful leave submission. With an existing synthetic 2 October shift, submitting leave for `2026-10-03T00:00:00+07:00` returned 409 as if it conflicted with that 2 October shift; submitting 3 October at 12:00 Bangkok time returned 201. The `/api/time-off` create route converted the supplied string to a `Date`, then derived `yyyy-MM-dd` using the server-local formatter. The UTC instant for Bangkok midnight fell on 2 October, explaining the observed conflict. That was the pre-fix staging result; the post-fix recheck is below.

The API creates time off without a persisted approval state in the current `employee_time_off` schema; this probe therefore verified submit and duplicate conflict, not an approval transition. A restricted role or branch-refusal check remains staging-unverified because no safe restricted login was available without the platform's SMS setup path. The tablet header overlap described in `scheduling.md` is also visible here, though the My Shifts leave card and Public Holidays list remained usable.

## Bangkok-midnight post-fix recheck on deployment `dep-daupqp60tbcc73c7ehv0`

With a labelled synthetic employee assigned to a 2 October shift, creating annual leave for `2026-10-03T00:00:00+07:00` returned 201. Repeating 3 October returned 409; creating leave for `2026-10-02T00:00:00+07:00` returned 409 against the actual shift. Moving the existing leave to 2 October returned 409; moving it to 4 October returned 200. This verifies the create and edit paths use the Bangkok calendar day for the conflict check. `scrum-193-staging-pa2-schedule-week.png` is a real 820-pixel staging view of the 2 October synthetic shift; `scrum-193-staging-pa2-leave-midnight.png` is a real signed-in browser capture of the stored time-off dates. The date and status assertions come from the route responses, not an inference from those images.

The approval limitation remained on deployment `dep-daupqp60tbcc73c7ehv0`. `PATCH /api/time-off/:id` with `approved: true` returned 503, but `POST /api/time-off` with `approved: true` and no shift on the target date returned 201 even though the row had no persisted approval field. That disposable row was deleted. The follow-up result on deployment `b20ed05b` is below. All PA2 leave, schedule, employee and holiday rows from the earlier run were removed; a read-only Data Admin sweep found no matching PA2 rows.

## Approval guard recheck on live source `b20ed05b`

On 1 October, using the existing launcher-signed staging administrator, an explicit `POST /api/time-off` with `approved: true` returned 503. A before/after `GET /api/time-off` returned 200 with no row created by that refused request. The ordinary Scheduling create payload, which omits `approved`, then created annual leave at Bangkok midnight on 3 October (201); a fresh read returned that one record (200). `PATCH /api/time-off/:id` with `approved: true` returned 503 and another read confirmed the ordinary row was unchanged. This verifies the route behavior using the payload now defined in Scheduling; this run did not click through the form. It does not prove a complete approval workflow, which still needs platform approval columns.

`scrum-193-staging-pa2-ordinary-leave-postfix.png` is a real 820 × 1180 staging browser capture of the created row, visually reviewed. The two 503 refusals are direct signed-in POST/PATCH response checks; a normal browser page cannot navigate to those methods for a response screenshot. The leave and synthetic employee were deleted (204 each). A final signed-in Data Admin sweep found zero matching PA2 employee-time-off and employee rows, along with zero PA2 rows in the other checked models.
