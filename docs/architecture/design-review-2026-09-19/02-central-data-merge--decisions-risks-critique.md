# DESIGN central-data-merge

## Summary
Use one Postgres database with one connection pool, split into a Postgres schema per module on top of a small shared kernel. The kernel is `core` (organisation, staff identity, access control, audit, files, migration provenance, privacy) and `crm` (members, children, consent).

Do the split now. Today the database holds only seed data in 37 tables, so the move costs days. After Sprint 2 tables and real data exist it costs weeks.

- **Identity:** staff and customer identity stay two separate aggregates joined by an explicit, audited link. A universal "person" table would mix two PDPA legal bases and two retention regimes in one row.
- **IDs:** every target key is a UUIDv7. Legacy keys never become columns. They live in `core.legacy_map`, and migrated IDs are derived deterministically from the legacy key so that two runs produce identical output.
- **ETL:** a TypeScript and SQL pipeline in a throwaway workbench database that runs land, profile, stage, resolve identities, transform, load, reconcile. Raw legacy data never enters the production cluster and never sits on a developer laptop.
- **Other apps:** each app is absorbed by freeze-and-migrate, one module at a time, with exactly one system of record per module. There is no dual-write. The launcher shows every app from day one by deep-linking to the legacy app until that module is cut over.
- **History:** closed history goes into analytics facts and an encrypted archive. Only open obligations and legally required records enter the new transactional tables.
- **Analytics:** Omni Analytics and Oto Radar read an `analytics` schema of rollups that holds no personal data and recomputes days touched by late offline events. They also read a few bounded "today" queries.
- **PDPA:** the current design is missing consent records, an erasure path that survives backups and re-runs, audit payloads that do not copy personal data, and a rule excluding biometrics and ID photos from migration.

The repository evidence points to Postgres on RDS. CLAUDE.md line 19 says so and nothing in the repo mentions MongoDB. The likelier hidden problem is that there are several datastores, one per Replit app. Confirm this with metadata before designing any mapping. Only the landing step differs if a source turns out to be MongoDB.

## Key decisions
- **Use one database and one pool, with a Postgres schema per module on a two-tier shared kernel (`core` plus `crm`). Restructure now, while the database holds only seed data.** — The 37 Sprint 1 tables sit in `public` under generic names (`employee`, `role`, `item`, `transaction`, `account`). These will collide with tables from the imported apps. Today the move is `ALTER TABLE ... SET SCHEMA` plus Drizzle `pgSchema` definitions, which costs days. After Sprint 2 tables and production data exist it costs weeks. One database keeps single-transaction integrity and satisfies the one-pool rule in brief section 9. (rejected: A single `public` schema with table prefixes gives no ownership boundary and no way to check foreign-key direction. A database per app breaks the central-database requirement and the one-pool rule. Schema-per-tenant is already rejected in ARCHITECTURE.md. Restoring each app's existing tables side by side into one database gives a shared server, not a central database.)
- **Keep one linear migration stream for the whole database, with hand-written SQL migrations for triggers, partitions and roles. Enforce module boundaries with a CI foreign-key-direction check and an ESLint import rule.** — Cross-schema foreign keys into `core` and `crm` need one ordering. The API deploys as one unit. The existing CI check that migrations apply twice from empty keeps working. drizzle-kit does not manage triggers or partitions either way. (rejected: Per-module migration folders and journals create ordering hazards across schemas and need several `__drizzle_migrations` tables. Per-module database roles add cost and no protection when one pool runs as one role.)
- **Do not add a universal person or party table. Staff identity (`core.employee` plus `core.account`) and customer identity (`crm.member` plus `crm.child`) stay separate, joined by an audited nullable link `crm.member.linked_employee_id`.** — The two sides have different PDPA legal bases (employment contract and legal obligation versus consent). Their retention clocks, de-duplication keys and erasure semantics differ too. A shared row would make erasure and purpose limitation hard, and it would expose HR data and customer data to each other. The link alone is enough for staff benefits at checkout (SCRUM-100 and SCRUM-101). (rejected: A full party supertype forces a join everywhere and mixes purposes. It also makes a phone shared by two people a hard constraint violation. Having no link at all leaves staff benefits and the "employee is also a customer" case without a home.)
- **Unify staff logins with `core.account_identifier` (phone, email, legacy username) and `core.credential`. Cut staff over by loading accounts as `invited` and using the existing SMS setup flow.** — Imported apps key users by email or username, while `account.phone` is NOT NULL and is the only login. Several legacy users must resolve to one account. SMS setup already exists and proves phone ownership. It also works whatever the legacy auth was: Replit Auth or Google would leave no hashes to migrate. Staff numbers are small. (rejected: A multi-algorithm password verifier as the primary path is kept only as a fallback if the client objects. Keeping a per-app user table is ruled out.)
- **All target keys are UUIDv7. Legacy IDs live only in `core.legacy_map`. Migrated IDs are deterministic and UUIDv7-shaped: the timestamp comes from the legacy `created_at` and the remaining bits from SHA-256 of the legacy key.** — Runs from an empty target then produce identical IDs. That makes "two runs match" a hash comparison, and it keeps index locality and chronological ordering beside native rows. Because `source_pk` is text, integers, UUIDs and MongoDB ObjectIds all fit. Many-to-one rows record merges. (rejected: Random UUIDv7 looked up from a persisted map makes determinism depend on carrying state between runs. A `legacy_id` column on every target table pollutes the model and cannot represent merges. Keeping integer keys is incompatible with box-minted IDs. Plain UUIDv5 works but loses time ordering.)
- **Run the ETL in a throwaway workbench Postgres on a controlled host. Raw legacy data never enters the production cluster or a developer laptop, and development uses a pseudonymised dump.** — The legacy dump almost certainly contains face biometrics, ID-document images, children's health notes and HR data that must not be carried over. The working directory is inside OneDrive. Transforming into the real target schema inside the workbench makes every constraint fire before production is touched. (rejected: `legacy_*` staging schemas inside production, or a local restore on a developer machine, which brief section 12 implies. dbt, Airbyte or pgloader add tooling weight for a small volume and a TypeScript team.)
- **Make the load idempotent and safe for delta runs: upsert by ID, guarded by `legacy_map.loaded_hash`, with `core.erasure_log` as a suppression list and an `unload --run` command.** — With per-module phased cutover the target is live while later runs happen. A re-run must not overwrite rows edited natively and must not resurrect erased people. It also has to be reversible per run. (rejected: Truncate-and-reload works only for an empty target under a big-bang cutover. Last-write-wins on `updated_at` fails because `updated_at` is set by the application through Drizzle `$onUpdate` and is not trustworthy.)
- **Absorb the other apps by freeze-and-migrate per module. Each module has one system of record, tracked in the module registry. Launcher tiles deep-link to the legacy app until the module's cutover. No dual-write is used.** — Dual-write across two codebases with different ID schemes and no transactions diverges silently. The API currently has zero `db.transaction` calls, and the legacy code is unmaintained tech debt. The launcher's module status lets the client see the full suite immediately with no data coupling. (rejected: Dual-write, request-time read-through to the legacy database (a runtime dependency plus legacy credentials in the production API), and a big-bang merge of all apps at once.)
- **For data the new platform needs while the old app is still master, use a one-way scheduled snapshot import of kernel tables. The imported rows are read-only and marked `mastered_by`.** — The employee list for staff benefits is the typical case. The new UI shows these rows read-only, with no runtime dependency on legacy uptime. The master flips in one place when the owning module cuts over. (rejected: Letting both systems edit employees, or making the new platform master of employees before the HR module exists. The second is acceptable only if the client agrees to stop editing staff in the old app.)
- **Migrate open obligations and legally required records into the transactional tables. Closed history goes into `analytics` facts plus an encrypted archive.** — The new ledger has strict invariants that legacy rows will not satisfy: immutable documents, station-prefixed numbering and a satang tax breakdown. Forcing history through them multiplies migration risk for little operational value. A 2 GB database should not carry dead weight. (rejected: Migrating all history into the new transactional tables, or keeping a permanent `archive_*` schema in production. Build an archive viewer only if the client names concrete lookup needs.)
- **Analytics reads only the `analytics` schema plus registered, bounded "today" queries. The schema holds no personal data, runs sliding-window recompute, and keeps a `dirty_date` queue fed by late offline sync.** — Brief section 9 asks for rollups before any read replica. Offline boxes deliver events days late, so closed days must reopen. Keeping personal data out of facts decouples analytics from erasure and retention. (rejected: Dashboards querying transactional tables freely, materialised views refreshed wholesale (too heavy on one CPU), and Radar or Omni connecting to the database directly.)
- **Treat PDPA as a schema concern now.** — Nothing personal is in production yet, so fixing audit payloads and delete semantics is cheap. Children's health data and HR data are sensitive under PDPA. `consent_recorded_at` and whole-row audit copies are insufficient. The foundations currently forbid the hard delete that `BACKEND_REQUIREMENTS.md` demands. The required pieces are:
- `crm.consent` records;
- audit diffs redacted at write time;
- `core.access_log` for sensitive reads;
- an erasure path (hard delete or anonymise in place) backed by `core.erasure_log`;
- a retention policy table with a nightly job;
- exclusion of biometrics and ID photos from migration. (rejected: Soft delete only, redacting audit rows after the fact, and deferring consent modelling until after migration.)

## Risks
- [critical] The source reality is unknown. There is the Postgres-versus-MongoDB discrepancy. More likely, there are several datastores, one per Replit app, and the single "production dump" covers only the OTO App. Schemas pushed with `drizzle-kit push` drift from the repo code. — MITIGATION: Run a metadata-only data-source inventory first: AWS describe calls, `kubectl`, environment variable names, `pg_restore -l`, and dependency and schema checks per repo. Treat the dump as the truth and the repo as secondary. Make the landing step a source adapter (Postgres restore, or MongoDB JSONL to jsonb) so nothing downstream depends on the answer. Write no mapping until the profile report exists.
- [critical] Production personal data handled unsafely by the development team. The working directory is under OneDrive. The dump likely contains children's health notes, HR data, national IDs and face biometrics. Rows could be pasted into Jira or AI tools. — MITIGATION: Write the dump-handling protocol before receipt.
- Transfer by presigned S3 with SSE-KMS.
- Store on an encrypted volume outside OneDrive.
- Add `.gitignore` patterns for dump files.
- Run the ETL on a controlled host inside the client's AWS account or a locked-down VM.
- Let developers work on a pseudonymised dump produced by a script the client runs.
- Sign a data processing agreement.
- Set a destruction date and issue a destruction certificate.
- [critical] False merges in identity resolution. Causes include shared or placeholder phones, foreign numbers typed without a country code and parsed as Thai, and `normalizePhone` using the lenient `isPossible()`. Merging two families would cross-contaminate children's allergy and medical notes. — MITIGATION: - Give every phone a class and record it.
- Quarantine high-frequency phones.
- Auto-merge only on an exact E.164 match.
- Send email-plus-name matches to human review, with decisions persisted by legacy key.
- Use union survivorship for health text.
- Force guardian reconfirmation at the next visit.
- Add a hard reconciliation assertion that no allergy text is ever lost.
- Use the same `member_alias` mechanism as the offline merge.
- [high] Schema restructure timing. Sprint 2 (box sync, sale ledger, wallets) is about to add many tables on top of a single `public` schema with placeholder tables. Every table added first raises the cost of the split. — MITIGATION: Do the `core`/`crm`/`edge`/`pos` schema split, the renames of generic tables and the kernel changes as the first Sprint 2 work item. The only data today is seed data. The 50 existing integration tests are the safety net.
- [high] Temporal and text corruption: Buddhist-era years, `timestamp without time zone` columns of unknown zone, mojibake or TIS-620 content, zero-width characters and Thai digits. Wrong timestamps in timekeeping data affect payroll. — MITIGATION: - Run profiling checks per column.
- Infer the zone from when events cluster, and confirm against known events.
- Apply Buddhist-era to Common-era conversion rules with a rejects table.
- Normalise to NFC.
- Strip zero-width characters.
- Cover each case with a synthetic fixture in CI.
- Have the client confirm one known payroll month end to end.
- [high] Money fidelity. Legacy amounts are probably floats or numeric baht. Rounding to satang can shift totals. Liabilities (stored value, deposits for future events and camps, staff vouchers) must carry over exactly. — MITIGATION: - Convert with explicit rounding and flag fractional satang.
- Reconcile per month, per branch and per method to the satang.
- Check liability tables per holder as well as in total.
- Have the accountant sign the liability reconciliation before go.
- [high] The interim master for shared kernel data. Employees, departments and branches are edited in the legacy OTO App while the new platform also needs them for permissions, staff benefits and the HR linkage. — MITIGATION: Keep a single declared master per entity, recorded in a `mastered_by` column. Import a one-way snapshot from legacy and show those rows read-only in the new UI. Flip the master at HR cutover. Confirm the SCRUM-158 organisation model before mapping.
- [high] Nobody maintains the legacy system, since the developer who built it has left. Freezing a module, creating a read-only database user or taking snapshots may have no owner on the client side. — MITIGATION: Identify who holds AWS and Kubernetes admin. Prefer database-level freezes, by revoking write grants per table for the application user. These need no legacy code change. Rehearse the freeze and unfreeze in advance.
- [high] Erasure versus immutability. Four things block or undo a PDPA erasure:
- the audit `before/after` payload copies personal data;
- ledgers and child-release records must be retained;
- backups, point-in-time restores and box SQLite caches hold copies;
- ETL re-runs can resurrect erased people. — MITIGATION: - Write audit diffs that are redacted at write time.
- Keep the ledger free of personal data, with a separate table for tax-invoice buyer details.
- Anonymise in place where rows are referenced.
- Re-apply `core.erasure_log` after restores and consult it in the ETL.
- Send tombstones through the sync feed.
- State the backup ageing window in the privacy notice.
- [high] Biometric and ID-document data in legacy. SCRUM-118 (face identity) is still "In Review", while brief sections 10 and 13 forbid biometrics and ID photos. — MITIGATION: A pipeline rule excludes these tables and S3 prefixes. Obtain a written client decision and a documented destruction. Deliver the PIN or badge alternative before timekeeping cutover.
- [high] Scope uncertainty. Eight apps and 58 X-stories are unseen. Brief section 2 assumes all remaining software is finished in Sprint 2. Per-module transforms cannot be written before the module's target schema exists. — MITIGATION: Commit Sprint 2 only to the ETL framework, profiling, kernel migration and customer migration. Size each module after its repo and profile are reviewed. Let the launcher's `legacy_link` tiles remove the pressure to migrate everything at once.
- [high] Open obligations at cutover: future-dated bookings, deposits, part-paid events, in-progress e-signatures, pending leave requests, open tasks and active vouchers. — MITIGATION: Build an explicit inventory of open items per module. Add reconciliation gates for each. Cut over at a natural boundary, such as a pay period or a quiet weekday. Carry original references as business keys so staff can find records.
- [medium] Migrating files and documents: signed contract PDFs with their signature evidence, SOP files and Fix media. Expect broken S3 references and orphaned objects. The target object store on Render is not yet chosen. — MITIGATION: - Reconcile the bucket inventory against the database during profiling.
- Copy with checksum verification.
- Use deterministic `file_object` IDs.
- Preserve contract bytes and evidence unchanged.
- Choose the target object store and region before rehearsal 1.
- [medium] Database capacity on the 1 CPU / 2 GB tier while the single pool is shared by bulk loads, rollups, the sync feed and dashboards. Related issues: `pg.Pool` has no `max` set (`packages/db/src/index.ts`), and change-sequence triggers fire on every bulk-loaded row. — MITIGATION: - Set the pool `max` and statement timeouts.
- Load with batched COPY or multi-row upserts.
- Temporarily upscale the instance for cutover loads.
- Run rollups at 03:00 with a sliding window.
- Put a semaphore on dashboard queries.
- Verify the plan's recovery window before relying on it.
- [medium] Tooling friction. drizzle-kit needs multi-schema configuration. Enums must move schema. Triggers and partitions sit outside drizzle-kit. `updated_at` is set only by the application, so ETL and cross-module writes would not bump it. — MITIGATION: Add a `schemaFilter` configuration. Write hand-written SQL migrations for triggers, partitions and roles. Add a database trigger for `updated_at` and the change sequence. Keep the CI job that applies migrations twice from empty.
- [low] Two sign-ins during the interim. Legacy tiles in the launcher open apps with their own auth, so "one sign-in" is only true for migrated modules. — MITIGATION: Set this expectation with the client and label legacy tiles. Do not build SSO into legacy apps. The gap closes as each module migrates.
- [medium] Messaging cutover is inherently a hard switch, because each channel webhook points at one endpoint. Conversation history may be large and full of personal data. — MITIGATION: Migrate the contact identities and open conversations. Archive the rest under the 12-month retention. Rehearse the webhook re-pointing in a sandbox. Schedule the switch outside peak hours.
- [medium] Cross-border transfer and controller duties. Hosting is in Singapore. A records-of-processing document is required because sensitive data is processed. There is a 72-hour breach notification duty. No privacy notice or consent wording has been seen. — MITIGATION: Raise these with the client's counsel now. Generate a records-of-processing skeleton from module manifests (data categories and purposes). Disclose the transfer in the privacy notice. Define the breach runbook.
- [medium] Conditional on a MongoDB source: schemaless drift, embedded arrays, ObjectId references with no enforced integrity, and dates stored as strings. — MITIGATION: Land the documents as jsonb, flatten them with views, and widen profiling to type-per-field histograms. Expect roughly 30 to 50 percent more staging effort for that source. The architecture does not change.

## Changes to Sprint 1 foundations
- New migration 0003: create the schemas `core`, `crm`, `edge`, `pos` and `analytics`. Move the 37 tables and 7 enums with `ALTER ... SET SCHEMA`. Convert `packages/db/src/schema/*.ts` to `pgSchema(...)`. Add `schemaFilter` to `packages/db/drizzle.config.ts`. Keep one migration journal.
- Rename the generic placeholders in `packages/db/src/schema/future.ts` while they are empty: `transaction` becomes `pos.sale`, `item` becomes `inv.stock_item`. Replace pgEnums that grow (`station_kind`, `contact_channel`) with text plus a CHECK constraint.
- Add `core.legacy_map`, `core.erasure_log`, `core.dsr_request`, `core.retention_policy`, `core.access_log` and `crm.consent`. The `child.consent_recorded_at` column in `packages/db/src/schema/members.ts` becomes a denormalised convenience at most.
- `crm.member`: add `merged_into_id`, `linked_employee_id` (with a partial unique index) and `consent_status`. Add `crm.member_alias`. Change the `child` to `member` foreign key from `ON DELETE CASCADE` to `RESTRICT`. Make `member.tier_code` a real foreign key, or validate it in the ETL.
- `core.employee` (`packages/db/src/schema/tenancy.ts`): add `employee_no`, `worker_type`, `status`, employment dates, `manager_employee_id` and `mastered_by`. Deep HR fields go to `hr.*`.
- `core.account`: relax `phone NOT NULL` and add `core.account_identifier` and `core.credential`. Fix `findAccountByPhone` in `apps/api/src/services/auth.ts`, which ignores the operator and would resolve ambiguously once merged data exists.
- `packages/shared/src/phone.ts`: add a legacy pre-normaliser and `classifyPhone()`. The pre-normaliser handles `66XXXXXXXXX` without a plus, Thai digits, zero-width characters and several numbers in one field. `classifyPhone()` exposes both `isPossible` and `isValid`. The ETL and the runtime must share this code.
- `packages/shared/src/ids.ts`: add `legacyId(sourceSystem, table, pk, createdAt)`. It builds a deterministic UUIDv7-shaped ID through `UUID.fromFieldsV7`.
- Audit (`apps/api/src/services/audit.ts` and `audit_log` in `packages/db/src/schema/platform.ts`): change `before/after` from whole-row copies to allowlisted field-level diffs with sensitive fields redacted. Add `origin` (with a `migration` value), `occurred_at` and monthly partitioning. Migration writes one audit row per run per table.
- Replace the blanket "no hard deletes" rule (CLAUDE.md section 3 and ARCHITECTURE.md section 4) with this one: soft-delete business records, plus a PDPA erasure path that hard-deletes or anonymises in place and is logged in `core.erasure_log`.
- Add a database trigger for `updated_at` and a change sequence on cacheable tables. Without it, ETL bulk writes and other modules' writes bypass Drizzle `$onUpdate` in `packages/db/src/schema/helpers.ts`, and boxes never see migrated or imported rows.
- `packages/db/src/index.ts`: set the pool `max` and a default `statement_timeout`. Expose a separate `analyticsDb` handle on the same pool.
- Fix the two tenant leaks reported by reconnaissance before any real data is loaded: `GET /members/:id` without an operator filter (`apps/api/src/routes/members.ts`) and `GET /public/member-tier` without an operator filter (`apps/api/src/routes/public.ts`). Denormalise `operator_id` onto branch-scoped tables.
- Create the database as UTF8 with ICU. Add a `th-x-icu` collation, `pg_trgm` and lower-cased email indexes.
- Add the workspace package `oto-platform/tools/migrate`, excluded from the API bundle, with a synthetic legacy fixture that reuses `createTestDatabase()` from `packages/db/src/testing.ts`. Add the dump-file patterns `*.dump`, `*.sql.gz`, `*.bson` and `*.archive` to `.gitignore`.
- Give the module registry a `status` of `legacy_link`, `pilot`, `live` or `retired`, plus an external URL. The launcher can then deep-link unmigrated apps, and the registry doubles as the record of which system is master for each module.

## Disagreements with brief
- Section 12 ("a repeatable migration into the Sprint 1 schema, run from a local restore"). The Sprint 1 schema is not the target. It must first be split into module schemas and gain identity, consent and legacy-map structures. "Local restore" on a developer laptop is unsafe, and this working directory is inside OneDrive. Run the ETL in a controlled workbench host and develop against a pseudonymised dump.
- Sections 2 and 14.7 (all remaining software, migration included, finished in one Sprint 2 run). With eight unseen apps and an unprofiled dump, only the ETL framework, profiling, kernel migration and customer migration can be committed. Per-module transforms depend on target schemas that do not exist until each app is ported. Split item 7 into a framework-and-kernel part done now and a per-module migration done at each module's cutover.
- Addendum ("merged into one system with a central database"). I agree with one database. I disagree with any reading that restores each app's existing tables side by side. Every app is re-modelled onto the shared kernel through the staging pipeline, and launcher tiles deep-link to legacy until then. Otherwise the result is a shared server with eight user tables.
- Section 9 (audit archived after twelve months, as a blanket rule). Retention should be set per action class. Child-release, incident and HR legal events need longer than twelve months. Session-level noise needs less. Audit payloads must stop copying personal data, or immutability will conflict with PDPA erasure.
- CLAUDE.md section 3 and ARCHITECTURE.md section 4 ("no hard deletes of business records"). This conflicts with PDPA erasure and with the project's own `apps/pos/BACKEND_REQUIREMENTS.md`, which requires a hard delete of child profiles. An explicit erasure and anonymisation path is needed.
- Section 4 (every box caches "members and children" from one identical image). For data minimisation, and because a Pi in a mall can be stolen, scope the cache by role. Counter boxes get members seen at that branch within N months plus today's bookings. Booth boxes get no member or child records, only a hashed-phone set for the one-spin rule. The box-sync architect owns this decision. It is flagged here because it is a PDPA exposure.
- Section 9 (1 CPU / 2 GB with one pool shared by everything). Keep the one pool. Plan a temporary instance upscale for cutover loads. Move rollups to 03:00. Give dashboard queries hard timeouts and a concurrency cap. Verify the plan's actual point-in-time recovery window, and note that a restore creates a new instance.

## Sequencing
- Week 0, before any dump arrives: send the data-source inventory questionnaire. Agree the dump-handling protocol covering transfer, storage outside OneDrive, the pseudonymisation script and the destruction date. Add the `.gitignore` patterns. Ask first for metadata only: `pg_restore -l` output and table sizes.
- Make the schema restructure the first Sprint 2 work item, ahead of any new feature tables: the module schemas, the renames and the kernel changes (employee, account identifiers, credential, legacy map, consent, erasure log, audit redaction). Do it together with the service-layer and transaction refactor the other reviewers call for. The existing 50 integration tests protect it.
- Build the ETL framework and its synthetic-fixture CI tests next. Then run profile #1 on the real dump in the controlled environment. The profile report, which has counts and no personal data, drives the mapping spec, the migrate/archive/drop verdict per table and the confirmation of the SCRUM-158 organisation model.
- Migrate the kernel first: operator or legal entity, branches, departments, employee identity, accounts and roles. The launcher can then ship with real users and `legacy_link` tiles for every unmigrated app.
- Migrate customers and children second, with identity resolution, the manual review queue and consent gating. POS depends on this before go-live.
- Build the `analytics` schema, `business_date` and the dirty-date recompute together with the POS sale ledger. Omni Analytics and Radar are re-pointed last, but the rollup contract has to exist when the ledger is designed.
- Absorb modules one at a time, in this order:
1. Wheel and Satang, as rehearsals.
2. Ops (tasks, checklists, SOP, Fix).
3. Timekeeping, scheduling and leave, at a pay-period boundary.
4. HR documents and e-signature.
5. Events and camps, carrying open bookings.
6. Inbox, with its webhook hard switch.
7. Analytics and Radar.
