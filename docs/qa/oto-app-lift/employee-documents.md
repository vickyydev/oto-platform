# SCRUM-193: employee documents and spreadsheet preview

## Access-matrix audit on live deployment 858df417, 1 October 2026

The earlier signed-in staging proof below already covers administrator upload, exact-byte private download, a wrong employee path, anonymous 401 and cleanup, so no duplicate document or employee was created for this audit. The document list, upload, delete and file handlers in `apps/oto-app/server/routes.ts` check the employee's signed-in tenant and permitted branch. The read handlers allow an authenticated employee in a permitted branch, but a positive employee self-download and a signed-in manager assigned only to another branch have **not** been observed on staging.

There is no safe reusable restricted staging session in the recorded QA: the earlier disposable restricted accounts were removed. The platform account-creation and new OTO App identity paths issue and deliver a setup SMS. A read-only Render check confirmed the staging API's configured SMS adapter is a delivering provider, so this audit did not provision another account. Linking an existing account avoids an additional setup message but does not make creation message-free. The app's legacy local-login route returned 403 on live staging. An administrator-issued temporary password would take over an existing person's account and invalidate its sessions. Without a non-SMS disposable account path or a designated existing test account, the same-tenant other-branch refusal and employee self-download remain open staging gates; the existing wrong-path 404 and anonymous 401 are not substitutes for them. No fixture or object was created in this audit.

Employee document upload now writes directly to the configured object store and records its object path. Reading and deleting a document requires an authenticated user with access to the employee's branch, and the document must belong to that employee. The generic file route refuses this private folder. Legacy local document paths remain readable within the old employee-document directory in development. Excel preview parses its bounded upload in memory and leaves no temporary file.

The existing `employees.spec.ts` browser flow passed against the isolated full seed. It created an employee, uploaded a sample image, read the exact bytes through the employee route, received 404 from the generic route and a different employee path, deleted the document, and received 404 on a later read. A generated spreadsheet returned a preview without creating an employee. The first attempt timed out while the add page was loading; the rerun passed after the existing test's navigation wait was raised. A focused local MinIO check uploaded, read and deleted an employee document through the app's S3 adapter, then removed the disposable bucket. The production build passed; inherited app typecheck remained at 578 errors with no new diagnostic in the changed area, and changed-line ESLint found zero diagnostics.

The source landed on main at `b3af4e52` and is live on oto-app-staging as Render deployment `dep-dau2vtp7lnhs73f7k8rg`. Staging health returned 200, anonymous document list/file routes returned 401, and the generic employee-document route returned 404. The authenticated upload and download are recorded below.

## Signed-in staging proof, 1 October 2026

A launcher-signed administrator created a labelled synthetic employee and uploaded a generated `STAGING TEST ONLY` PNG as an ID document. The upload returned 201 and a private employee-document path; the document list returned 200 with one matching row. The authenticated file route returned 200 with the exact 4,859 bytes uploaded, `image/png`, `Cache-Control: private, no-store`, inline disposition and `X-Content-Type-Options: nosniff`. The real 820 × 1180 staging employee editor displayed the uploaded row in `scrum-193-staging-employee-document.png`; that screenshot was visually reviewed.

Anonymous document list and file requests returned 401. A second labelled employee at another branch could not use their employee path to fetch the first employee's document (404), and the generic private-file path returned 404. This tests ownership/path isolation; it does not prove refusal to a signed-in user whose account is restricted to the other branch. A safe restricted account was unavailable without invoking the platform's SMS setup path, so that branch-role staging gate remains open.

The document was deleted through its normal employee route (204), and the same file route then returned 404. Both synthetic employees and their activity rows were removed with 204; final searches found zero matching employees, employee documents or activity entries. The object is deleted by the document route before its row, so the post-delete 404 checks the storage cleanup path as well as the record path.
