# INTEGRATION

## Contradictions
- **offline-trust-money vs box-agent-sync vs ops-scale-delivery (band signing), and all of them vs the client-approved wristband design**: Three incompatible band schemes are proposed: per-box Ed25519 keys with a 41x41 QR (offline-trust-money); a per-branch HMAC key with day-derived subkeys held 30 days ahead (box-agent-sync); a per-branch HMAC rotated monthly with an 80-bit tag, never on booths (ops-scale-delivery). With either HMAC scheme the gate box must hold the forging key. None of the proposals noticed that the approved band is a thin black-ink strip carrying a 1D barcode, not a QR (C:/Users/waqar/OneDrive/Desktop/Projects/oto-pos/.agents/memory/print-templates.md and C:/Users/waqar/OneDrive/Desktop/Projects/oto-pos/oto-platform/apps/pos/src/components/till/Barcode.tsx). A Code128 barcode cannot carry a 64-byte Ed25519 signature, and CLAUDE.md section 7 forbids changing the approved design without the client. — RESOLUTION: Define one versioned token envelope in packages/tokens (prefix, algorithm id, key id) so the algorithm can change without touching callers. Decide the band format by a print-and-scan test on real 4B-2082A band stock with the Zebra DS22 and an iPhone camera in the week-1 hardware spike. Preference order: (1) per-box Ed25519 in a 2D code, keys certified by the cloud; (2) per-branch HMAC with day subkeys and a truncated tag, keys only on counter and gate boxes. Cloud-minted codes (bookings, staff tokens) are asymmetric in every case. Get written client approval for moving the band from a 1D barcode to a 2D code before building.
- **offline-trust-money (token bound with aud=box_id) vs ipad-box-network (re-home a station to a sibling box while offline) vs the offline-trust-money critique (iPad fans out a lookup to every counter box)**: A shift token whose audience is one box cannot be used on a sibling box when the cloud is unreachable, because only the cloud can mint a new one. That breaks rung 3 of the networking failure ladder and the iPad-mediated child-release lookup, which both need the same token to be accepted by several boxes in the branch. — RESOLUTION: Make the token audience the branch (aud = branch id) and carry: session id, session class, perm_version, expiry, and a reserved cnf claim for later proof of possession. Per-box exclusivity comes from the box-issued lease with a fencing epoch, not from the token audience. Renew the cloud token silently at half-life while online; when the cloud is down the box issues a box-local session flagged offline.
- **box-agent-sync (pushes the argon2 password unlock verifier, and sends PIN and badge hashes to every box) vs offline-trust-money, ipad-box-network and ops-scale-delivery (PIN only, never password hashes on a Pi) vs suite-platform and ops-scale-delivery (POST /api/auth/unlock at the cloud) vs ipad-box-network (the cloud must never accept the PIN)**: There are four different answers to 'what secret unlocks a till, where is it verified, and which boxes hold the verifier'. The box-agent-sync critique even asks for password verifiers on all counter boxes for failover, which the trust design explicitly rejects because the same password will guard HR and finance. — RESOLUTION: One credential model in core.credential with a kind column. Password: verified by the cloud only, never replicated. PIN: low-value, verified only by boxes, synced only to the counter boxes of the staff member's branch, rotated when a box is revoked. Badge: a cloud-signed credential, so boxes hold a public key and no secret; booth boxes accept badge plus PIN for booth staff only; gate boxes hold no staff verifiers. Manager approval is a separate signed approval (own phone) and is never the unlock PIN.
- **suite-platform (the POS lock becomes local and keeps the suite-wide cookie) vs its own critique (server-side session.locked_at returning 423 on every route) vs offline-trust-money and ipad-box-network (unlock happens on the box, offline)**: A purely local lock leaves /team/, /admin/ and /satang/ open in a new tab on a shared counter iPad. A server-side lock cannot be cleared by a box unlock while the internet is down, so the till would work through the box while the cloud session stays locked. The 12-hour fixed session expiry (SESSION_TTL_HOURS=12 in C:/Users/waqar/OneDrive/Desktop/Projects/oto-pos/oto-platform/.env.example) also ends a shift mid-outage. — RESOLUTION: Introduce session classes. A 'station' session is created on an enrolled shared device, is limited to device-facing modules (POS, check-in, F&B) and can never open HR, finance, admin or analytics, so a local lock is sufficient there. A 'personal' session gets the server-side lock and step-up authentication for sensitive modules. Sessions get revoked_at instead of being deleted, so session ids can appear in revocation lists. Fast user switching ends the previous station session; it never inherits it.
- **suite-platform (entitlements, account-level allow/deny, page and feature toggles, new self/reports scopes, evaluator in packages/authz) vs box-agent-sync, offline-trust-money and ops-scale-delivery (move only grantCovers/hasPermission into packages/shared and cache 'accounts and roles' on the box)**: A box that evaluates roles only would ignore an account-level deny, a switched-off feature such as manual discount, or a disabled module while offline. The package location also differs (packages/authz vs packages/shared), and the trust critique assumes grants travel inside the token while the sync design assumes they are cached rows. — RESOLUTION: One evaluator in packages/authz used by API, frontends and the box agent. The cloud compiles each account's final grant set (after entitlement, role union, allow and deny) into flat per-account rows that are synced to boxes as their own scope; the token carries perm_version, not grants. The box applies the restricted offline overlay from the trust design on top. The revocation list is built from live tables and repeated in every heartbeat acknowledgement so it bypasses a stalled feed.
- **suite-platform (one module key = permission namespace = pg schema = API prefix = folder) vs central-data-merge (core, crm, edge, pos, inv, analytics) vs ops-scale-delivery (core, pos, hr, sched, ops, events, inventory, msg, booth) vs box-agent-sync (sync schema) vs offline-trust-money (core.sync_event, core.signing_key) vs the existing permission strings**: The proposals name different schemas for the same things (inv/inventory/stock, sync/edge/core, care/crm). The existing permissions in C:/Users/waqar/OneDrive/Desktop/Projects/oto-pos/oto-platform/packages/shared/src/permissions.ts are pos:member:*, catalog:* and admin:*, while members and children are placed in crm by the data design. Under the 'one key' rule those strings, the role_permission rows and every guard must be renamed. The data-merge critique also adds a commerce tier that no proposal includes. — RESOLUTION: Freeze one module map before migration 0003: core, crm, commerce (payment, ledger document, voucher/entitlement, booking, attendee), catalog, pos, edge (box, station, device, device session, signing keys, change feed, event ledger), analytics, then one schema per imported domain. Rename pos:member:* and pos:child:* to crm:* in the same migration while the database holds only seed data. Record the map in the registry package and make CI reject a table, route or permission outside its module.
- **suite-platform (foreign keys only into core) vs central-data-merge (foreign keys into core and crm, all others banned) vs box-agent-sync (references are soft, projectors tolerate missing parents) vs the data-merge critique (declared dependency graph plus commerce)**: A blanket ban discards referential integrity exactly where the merge needs it (event deposits to payments, vouchers to redemption, staff benefits to employees), while hard foreign keys make box event projection throw when a parent arrives later. C:/Users/waqar/OneDrive/Desktop/Projects/oto-pos/oto-platform/packages/db/src/schema/future.ts lines 85 and 127 still use ON DELETE CASCADE on ledger tables. — RESOLUTION: Declare an acyclic module dependency graph; foreign keys are allowed along its edges and a CI information_schema check enforces the allow-list. Rows that originate on boxes use soft references registered in a core.soft_ref catalogue with a nightly orphan alert. Remove every ON DELETE CASCADE from ledger tables and change child to member from CASCADE to RESTRICT in migration 0003.
- **suite-platform and ops-scale-delivery (legacy dumps land in legacy_<app> staging schemas inside the central database) vs central-data-merge (raw legacy data never enters the production cluster; throwaway workbench)**: Direct contradiction on where children's health notes, HR data, face templates and third-party tokens from the dump are allowed to sit. — RESOLUTION: The data design wins. Only finished rows and core.legacy_map reach production. Add the critique's 'production key snapshot' step (ids, normalised phones, business keys, row hashes pulled into the workbench) so collisions with native rows are detected once the target is live, and widen the legacy_map key to (source_system, source_table, source_pk, target_table, sub_key).
- **box-agent-sync (trigger-written sync.change feed with keys only, xid8 guard, one cursor per scope) vs ops-scale-delivery (a row_version column from one sequence on every cached table) vs central-data-merge (updated_at trigger plus a change sequence on cacheable tables)**: Three different change-tracking mechanisms for the same down-sync. A row_version cursor has exactly the commit-order race the feed design identifies, cannot express a row leaving a scope, and gets rewound by a point-in-time restore. The feed's own cursor is also wrong unless it is a tuple. — RESOLUTION: One mechanism: a feed table in the edge schema, written by hand-written SQL triggers, cursor = (transaction id, sequence) compared as a tuple, change rows emitted for both the old and the new scope when a scope column changes, and a feed epoch stored outside the restored data that forces a full re-bootstrap after any restore. Importers and rollups commit in small batches, and every role gets idle_in_transaction_session_timeout, because the visibility watermark is database-wide once HR, analytics and the importer share the database.
- **box-agent-sync, offline-trust-money and ops-scale-delivery (HTTP routes and box ingest share one transactional write path; projection and audit in the acknowledging transaction) vs all three critiques (store first, project later) vs offline-trust-money's own outcome list (applied, duplicate, flagged, rejected) against its rule that facts are never rejected**: A projection error would roll back the only cloud copy of a sale or a child release, one poison event blocks a box's queue, and ON CONFLICT DO NOTHING without a target silently drops a different event that reuses a box sequence after a journal rollback. 'Shared write path' also conflates commands (which may be refused) with events (which already happened). — RESOLUTION: Two phases. Phase 1 stores the raw signed event and acknowledges; acknowledgement means stored, nothing more; dedupe with ON CONFLICT (event_id) only, and key order on (box_id, journal_epoch, box_seq) with a fork lane for a reused sequence. Phase 2 is a per-box ordered projector worker with states projected, flagged, held (excluded from spendable balances and fiscal exports until a human clears it) and parked (alerts, pauses only that box's projection cursor). HTTP commands validate, then emit the same event into the same applier, so online bookings and back-office refunds use identical projection code.
- **offline-trust-money (one aggregate event per business fact, e.g. sale.finalised carrying sale, lines, attempts, bands, wallet entries, cash movement and audit) vs box-agent-sync (fine-grained fact events with soft references) vs offline-trust-money's own write-ahead payment attempt**: If only the finalised aggregate is synced, the cloud never learns about a captured payment attached to an unfinished sale, which is the exact case the 2C2P orphan check and the 'cancelled with captured tender' state depend on. — RESOLUTION: Aggregate per completed business fact, plus lifecycle events for payment attempts (opened, resolved, abandoned) and supervision (check-in, release) that carry the same box-minted entity ids. Projectors upsert by entity id so both shapes commute and can be property-tested by shuffling ingest order. Every sale event is self-describing (unit price applied, rate mode, tax rule, discount definition, domain version) so cloud verification is arithmetic, not a catalog lookup.
- **box-agent-sync (sync.event partitioned monthly with unique event_id; audit_log with composite key plus unique source_event_id) vs offline-trust-money (unique source_event_id on audit_log) vs ops-scale-delivery (unpartitioned sync_event; audit_log partitioned on recorded time; dedupe through the ledger)**: PostgreSQL cannot enforce a unique index on a partitioned table unless it includes the partition key, so two of the three designs cannot deliver the permanent dedupe they rely on. Table and schema names also differ (sync.event, core.sync_event, sync_event, core.sync_inbox). — RESOLUTION: One unpartitioned event ledger in the edge schema (a few million rows a year). audit_log is partitioned monthly on server-recorded time with no unique index on source_event_id; audit idempotency comes from the ledger-guarded projector. Audit retention is set per action class (money and child release at least five years pending the accountant), not the brief's blanket twelve months.
- **the brief (boxes delete queue items once acknowledged) vs ops-scale-delivery (keep acknowledged events 14 days) vs its critique (400 days) vs the data-merge critique (restore window plus margin) vs ops-scale-delivery's own 35-day off-site dump horizon**: A cloud restore older than the box retention window permanently loses tax-invoice-numbered sales and release records that the boxes were told were safe. — RESOLUTION: Boxes retain acknowledged events for at least the longest restore horizon in the runbook (default 90 days, size-capped, money and release events last to be purged). The connect handshake returns the cloud's applied-through position, head hash and highest receipt number per series, and the box replays or jumps its counters accordingly. Verify Render's real point-in-time window before quoting any rollback period to the client.
- **the brief, ipad-box-network and box-agent-sync (certificates, revocations, 2C2P results and config pushed over an in-memory WebSocket hub) vs ops-scale-delivery (WebSocket carries pokes and commands only; data over idempotent HTTPS batches; box_command rows fanned out by NOTIFY)**: An API deploy or crash drops every socket and any in-flight payment result or revocation; nobody except the critiques defines the synchronous box-to-cloud call that 2C2P, wallet authorisation above the cap, single-use redemption and member cache misses all need. — RESOLUTION: Adopt the pokes-only WebSocket with a durable per-box command table and cursor. Add a small edge RPC surface with device-signed requests, the staff token forwarded, 3 to 5 second timeouts, and idempotency on an entity id minted by the box before the call, so the online call and the later fact event collapse into one row (this removes the wallet double-debit and the false double-redemption). Ping every 20 to 25 seconds to survive carrier NAT.
- **suite-platform (one Fastify process, in-process Postgres queue) vs ops-scale-delivery (one process with PROCESS_ROLES) vs box-agent-sync (pg-boss on the shared pool) vs ipad-box-network (in-process virtual box on synchronous SQLite plus two WebSocket hubs) vs the networking critique (separate box-gateway service) vs the brief's one-pool rule**: An analytics query, an AI stream or a synchronous SQLite apply in the same 1-CPU event loop stalls box pings and sync ingest, and every HR hotfix disconnects every box during trading hours. On Render a second service is necessarily a second pool, so the brief's rule cannot be literally kept. — RESOLUTION: One codebase with PROCESS_ROLES from day one and one queue library (pg-boss). Deploy two Render services when the first real box ships: 'edge' on the api hostname (sync ingest, box WebSocket, RPC, webhooks, station-token, key set) which deploys rarely, and 'suite' on the app hostname. Boxes and webhooks never need the staff cookie, so no path routing between services is required. Treat the one-pool rule as a published connection budget. No SQLite inside the API process.
- **ipad-box-network (production 'cloud mode' is the box agent hosted in-process as a virtual box per branch) vs box-agent-sync (remote mode is management and reporting only, selling disabled) vs ops-scale-delivery (no remote till, yet one contract suite run against both cloud and box servers) vs the brief ('the app must not care which')**: Disagreement on whether the cloud must implement the whole station contract. Meanwhile cloud-originated sales exist regardless: online bookings, event deposits and payments (SCRUM-142) and back-office refunds. — RESOLUTION: Keep buildAgent hosted in-process only as the staging and convergence-test harness. Production cloud commerce uses packages/domain plus the same event applier and its own cloud receipt series; reads come straight from Postgres. Whether staff ever sell off-site is an owner question; if yes, revisit a separately deployed virtual box after load-testing the cache rebuild against the production member count.
- **suite-platform and ops-scale-delivery ('API and all frontends deploy atomically, so contract skew is impossible') vs ipad-box-network (skew is the normal state; capability handshake) vs three critiques (release the POS on its own cadence; evaluate serving the till from the box as primary; isolate the POS on its own origin for XSS containment)**: The installed iPad web app and the boxes are routinely older than the cloud, so atomic deploys do not prevent skew, and every back-office hotfix would push a new till shell mid-shift. Serving the till from the box or a separate origin conflicts with 'one origin gives free single sign-on'. — RESOLUTION: Default: till served from the cloud at /pos/ but released on its own channel from a versioned asset directory; service-worker update applies only at the lock screen with no open sale; API changes additive-only within a major version; an X-OTO-Client header with a typed CLIENT_TOO_OLD response; CI tests previous till against current API and agent, and current till against previous agent; exhaustive switches in packages/domain so an unknown rule kind refuses the line instead of mispricing (packages/shared/src/pricing.ts resolveAdultLine falls through today). Record an explicit decision on the box-served till after the week-1 iPad spike, because it changes token storage, CORS and the launcher hand-off.
- **the brief, ops-scale-delivery and ipad-box-network's main text (box hostnames under central.otoplay.co) vs suite-platform and the networking critique (a separate registrable domain plus a __Host- cookie)**: Under the company domain every box is same-site with the staff app: a stolen Pi with a valid sibling certificate can toss cookies and send same-site requests, and internal topology is published in certificate transparency logs under the brand. The cookie in C:/Users/waqar/OneDrive/Desktop/Projects/oto-pos/oto-platform/apps/api/src/plugins/session.ts is plain oto_session with SameSite=Lax. — RESOLUTION: Buy a separate inexpensive domain for box names before any hostname is baked into certificates, station records or installed displays. Production cookie becomes __Host-oto_session, plus an Origin check on every mutating request and trustProxy. Address boxes by box name, not by station name as in the brief's example, because stations can be re-homed.
- **ipad-box-network (the cloud issues certificates and pushes them to boxes) vs box-agent-sync and ops-scale-delivery (the box generates the key and a signing request; the cloud performs DNS-01 and returns the certificate)**: In the first design box private keys transit and are known to the cloud; in the second they never leave the box. — RESOLUTION: Signing-request brokered issuance. Booth and kiosk-only boxes use localhost and need no certificate. Report certificate expiry in the heartbeat and renew at half-life; the warm standby must be enrolled and renewing, not cold in a drawer.
- **suite-platform (strangle code not traffic; one rehearsed cutover for the OTO App; no single-sign-on bridge into legacy) vs central-data-merge (freeze-and-migrate module by module, steps 2 to 7) vs ops-scale-delivery (fold modules in one at a time after POS go-live; add a signed sign-on handoff) vs all critiques (system of record must be defined per entity)**: Per-module cutover of one unmaintained legacy monolith cannot be frozen table by table, and any 'POS first' order leaves child health data, pickup authorisation and employee records edited in two live systems for months. The proposals also disagree on whether to build a sign-on bridge into legacy. — RESOLUTION: The registry records the owning system per ENTITY (child, member, employee, branch, department). Legacy stays master for employee, department and branch through a one-way nightly import keyed by core.legacy_map, read-only in the platform, until the People cutover. All child-facing legacy functions (camp registration, drop-off forms, nanny and camp check-in with handoff) move in the same wave as POS supervision. The staff-side OTO App moves in at most two cutovers at a pay-period boundary; leaf modules (SOP, Fix reports, tasks, announcements) may go earlier. Build a sign-on bridge only if intake shows legacy auth is a single middleware; otherwise tell the owner in writing that legacy tiles keep their own login.
- **suite-platform (account.email, core.account_identity, unique role (operator_id, key)) vs central-data-merge (core.account_identifier, core.credential, phone no longer NOT NULL) vs offline-trust-money (core.account_credential) vs ops-scale-delivery and the data-merge critique (unique role (operator_id, name))**: Three overlapping table designs for staff identity and credentials, and two different uniqueness keys for roles, all touching the same Sprint 1 tables in C:/Users/waqar/OneDrive/Desktop/Projects/oto-pos/oto-platform/packages/db/src/schema/tenancy.ts. — RESOLUTION: core.account_identifier (kind: phone, email, legacy username) and core.credential (kind: password, pin, badge, totp). Roles are unique on (operator_id, key) with a separate display name and an is_system flag. No legacy role grant is migrated; accounts load with zero assignments from a client-signed mapping sheet, invites expire, and findAccountByPhone becomes operator-aware.
- **the brief and ipad-box-network (2C2P is the primary in-person QR; the box fetches and serves the 2C2P QR image and switches to the PAX QR automatically) vs offline-trust-money (Digio QR payload on the customer display is primary on the PAX station; 2C2P only where there is no PAX; the merchant secret never on a Pi)**: Opposite primaries, and 'the box fetches the QR' implies the box talks to 2C2P. - **central-data-merge (a PDPA erasure path that survives backups and re-runs) vs box-agent-sync and offline-trust-money (permanent signed raw event ledger, hash chain, triggers that block UPDATE and DELETE) vs the ops-scale-delivery critique (boxes retain acknowledged events for 400 days)**: Events such as member created, child updated or pickup person added carry names, phone numbers and allergy text. The iPad envelope copy is best-effort and never appears in a recovery runbook. Receipts print only after the journal fsync.
- **the brief ('Sprint 2 is one continuous run that finishes all remaining software') vs suite-platform (platform kernel first, estimated 1 plus 2 weeks) vs box-agent-sync (weeks 0 to 10 on the box alone) vs ops-scale-delivery (launcher first; 50 to 75 engineer-weeks POS plus 25 to 40 suite, with a further 25 to 45 unpriced according to its critique)**: The proposals sequence different things first and their foundation lists, added together, exceed what one developer can land before a till sells a ticket.
