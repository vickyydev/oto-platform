SCRUM-186 — S2-01a — Security and lock-model fixes
Dev evidence 2026-09-20 on commit 9312c69 (branch main, merged from feat/s2-01a-security-lock-model). Local stack: Fastify API + Postgres 16 (embedded per test file), ported POS. Full suites: 19 shared unit tests, 81 API integration tests, typecheck, lint and production build all clean. The four tests this ticket asks for by name are in apps/api/test/security.test.ts (17 cases).

Dominance: a branch_manager assigning platform_admin at operator scope → 403 ROLE_NOT_DOMINATED; a temp password for the operator admin from the same manager → 403 ROLE_NOT_DOMINATED; an account in another operator → 404 ACCOUNT_NOT_FOUND, never 403, so an id cannot be confirmed. The platform-wide scope (operator scope with a null id) is refused one step earlier, by scope ownership, with SCOPE_NOT_OWNED — both branches are covered by tests. Every refusal by a signed-in caller now writes an access.denied audit row carrying the code, the method and the URL with its query string stripped; GET /audit gained an action filter and the Login Users panel lists the last ten as "Recent denials".

Forged X-Forwarded-For: with TRUST_PROXY at 0, nine sign-in failures claiming nine different client addresses all land in one bucket keyed ip:127.0.0.1 — the test asserts the row set, not just the 429, so it shows WHY rather than only that it refused.

Throttle survives a restart: the cooldown is set, the api instance is thrown away and rebuilt against the same database (what a Render deploy does), and the next attempt is still 429. Sprint 1 kept these counters in a Map, so a deploy handed an attacker a fresh five guesses.

pg-error redaction: a fixture of the real node-postgres 23505 error for member_phone_unique — whose detail field reads Key (operator_id, phone)=(…, +66811111111) already exists — is reduced to pgCode, constraint, table and routine; detail, hint, where and parameters are dropped, and the serialised result is asserted not to contain the number. A duplicate member creation returns 409 MEMBER_PHONE_EXISTS with the phone in neither the body nor the log. MEMBER_EXISTS and ACCOUNT_EXISTS were renamed to MEMBER_PHONE_EXISTS and ACCOUNT_PHONE_EXISTS so the pre-check and the racing path answer with one code.

Rate limits: ten password-reset requests for one phone → 200 for the first five, then 429 (per-phone bucket, 5 in 15 minutes, counted in Postgres). A generous per-IP bucket sits behind it (120 a minute by default) because the mall shares very few public addresses. A sixth wrong setup or reset code invalidates every outstanding code for that account and purpose — the real code stops working too, which is the point; a newly issued code starts a fresh budget.

Lock model: locking keeps the session (POST /auth/lock), a locked session cannot call a business route (423 SESSION_LOCKED) including requireAuth-only ones, GET /me still answers so the screen can say who is locked out, and the password unlocks the same session under the sign-in throttle. Sign out is the only user sign-out and now revokes rather than deletes the row, so who ended a session survives for audit. Force sign-out ends every session an account holds, audited session.force_sign_out, and the evicted cookie is refused on the next call.

Also closed here: mustChangePassword is enforced in requireAuth rather than only in requirePermission — a temp-password account could otherwise reach every requireAuth-only route; /public/member-tier now requires its branch because phone is unique per operator, not globally; an Origin check guards state-changing requests; x-request-id is only honoured in the shape ^[A-Za-z0-9._-]{8,64}$; Fastify's own request logging is replaced by one completion line with the query string stripped, and the SMS adapter logs a phone hash instead of the number.

QA (UI) steps 1-4 on the ticket are for the owner to run against the Render deployment once S2-01c lands; the UI they exercise is in place — the locked lock screen, the Sessions dialog, "Sign out everywhere" and "Recent denials" on the Login Users panel.

Deferred to S2-01b as the ticket states: database transactions (withTx), the schema move, and the atomic idempotency claim.
